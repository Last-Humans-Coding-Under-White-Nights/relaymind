# RelayMind Specification for Spec Driven Development

Version 0.51 | 29 October 2026 | Proposed implementation baseline

RelayMind is a local AI gateway that makes the best use of external language models from a PC with limited resources: it keeps simple, bounded work on a small local model when the machine can run it fast enough, sends everything else to an external model with as few round trips and tokens as the task allows, preserves completed work across that switch, and shows every decision in a trace. This specification defines the prototype behavior, interfaces, acceptance criteria, and evidence required before making performance or quality claims. It is intended for engineers and coding agents implementing the prototype.

SDD means Spec-Driven Development here. MUST and MUST NOT identify acceptance requirements; SHOULD identifies a preferred implementation. Numerical budgets and evaluation thresholds below are proposed product decisions, not measured model capabilities. No prototype benchmarks have been run for this specification.

## 1 Product objective and scope

The prototype MUST demonstrate that the local model can select a skill, choose tools and arguments, consume actual execution results, and finish a simple task without an external model call. It MUST also demonstrate transfer of completed work to an external model, with visible attribution of skill selection, tool proposals, execution, and final output.

The agreed requirements are English interaction, with Chinese interaction supported on a best-effort basis, macOS and Windows execution, replaceable models, an OpenAI-compatible entry point, shared skills and tools, and observable routing. Qwen3-0.6B is the initial local candidate; the earlier approximate 300M size is no longer a constraint. The 500 ms first-response objective remains an experimental target.

The implementation baseline adds these decisions: a single-user local service, Python with FastAPI, a separate llama.cpp server process, SQLite execution records, trusted local skill packages, and a small deterministic demo tool service. The external provider and model are operator configuration, not hard-coded product dependencies.

| Priority | Included behavior |
| --- | --- |
| P0 | Local skill selection and tool loop; clarification; escalation; external completion; model adapters; trace UI; cancellation; simulated destructive action with confirmation; API conformance; evaluation (English required, Chinese best-effort) |
| P1 | One bounded parallel workflow with independent read-only branches; exact routing cache experiments |
| Outside this prototype | Token-level speculative decoding; replacing already streamed answer text; universal agent compatibility; arbitrary shell execution; production database deletion; production multi-tenancy; native desktop installers; general PDF ingestion; automatic skill installation; MCP connector marketplace |

The complete demo includes P0 and the bounded parallel workflow. Routing-cache experiments may follow the uncached baseline. General PDF processing is excluded because the earlier PDF example illustrated latency, while the agreed prototype now centers on skills and tools.

Phase 2 scope (introduced in spec 0.31, revised in 0.47). The current direction is: the gateway considers the measured performance of the device when it chooses between local and external work and never assumes that local inference is faster (RM27); it works without a local model, with external models, skill and tool selection, and progress feedback (RM26); it can serve as an OpenClaw provider plugin, with OpenClaw owning its tools and sessions (RM33); and its selection logic sits behind one interface that a third-party system can replace (RM28). The objective of the phase is the project's purpose stated above, the best use of an external model from a machine with limited resources, measured as shorter waiting time for the first useful response and for the completed result and as external calls and tokens per completed task, per section 12; the mechanisms are fewer generations and round trips (RM29, RM31, section 4.3), gated answer streaming (RM32), and placement from recorded timing samples (RM27). Phase 2 classifies a machine by what the gateway measures on it, never by its hardware type: suitable (the local model runs, and the measured samples predict that local work fits its budgets), unsuitable (the local model runs, but too slowly to help; the gateway detects this itself and uses managed external execution in auto, while local_only remains available, RM26), and none (the local model cannot run on the machine, or is not configured). The evaluation names each machine with its measured class. The reasoning behind the phase is in `docs/design/2026-10-23-performance-first-routing.md`; this document is the normative text.

Simplified Chinese, English and mixed-language retrieval are required under section 12.6; historical best-effort Chinese labels and frozen earlier evaluations remain unchanged. Recommendations rank skills and independent MCP tools; acquisition, manual installation/setup and host execution are separate. No automatic installation, gateway MCP client/server spawning, host prompt/tool pruning, new executor, multi-asset workflow planner or automatic asset-need classifier is included. There is one M10 milestone; the early installed-skill trial is delivery order within it.

Customer decisions approved on 29 October 2026: consumption covers the whole host task; one-second readiness measures gateway startup to useful lexical service over committed full-catalog metadata, separately from OpenClaw startup; early trials use explicit imports and full M10 completion requires scheduled refresh of a permitted qualified source. Other finite limits in this revision are builder decisions and acceptance targets, not customer approval or measured capabilities.

This revision freezes the independent core (catalog, discovery, selection v2, API and backend authorization) and preserves every full M10 gate. It adopts the qualification disposition in the [M10 design](design/2026-10-29-multilingual-asset-routing.md): where evidence is missing, MATRIX-COHORT, MATRIX-OVERLAP, MATRIX-RIGHTS, MATRIX-REFRESH, HOST-ACTION-AUTHORITY, HOST-EXACT-SKILL-USE, HOST-MCP-BINDING and HOST-MCP-CURRENTNESS remain blocked. Their adapter contracts are not implementation-ready. Runtime recommendation fails closed under section 7.6; no arbitrary host snapshot is accepted. Further supported qualification and a subsequent normative adapter revision are required before enabling those host paths. This costs a later revision; it does not authorize a host upgrade, alternate dataset or reduced milestone scope.

## 2 Verified foundations and limits

The following statements are externally grounded. Other implementation behavior in this document is a RelayMind design decision.

| Evidence | Established fact | Consequence for RelayMind |
| --- | --- | --- |
| S1 | The Qwen3-0.6B card documents non-thinking mode and an agentic example using this model identifier. | Use it as a candidate. This does not establish reliable bilingual skill execution or a 500 ms response on our hardware. |
| S2 and S3 | Tool calling requires model output formatting and application-side parsing and execution. llama.cpp documents tool-calling configuration. | Pin and test the model, chat template, parser, quantization, and runtime together. |
| S4 | llama.cpp documents Windows builds and a Metal backend for macOS. | Use a common runtime family, with separate platform qualification. |
| S5 and S6 | Chat Completions defines streamed deltas and function-call messages; the application executes custom functions and returns results. | Distinguish gateway-owned tools from client-owned tools. The supported contract is explicitly bounded below. |
| S7 | Agent Skills defines a SKILL.md package and progressive loading. Its allowed-tools field is experimental. | Reuse the document shape; enforce permissions in RelayMind configuration, not merely in skill prose. |
| S8 | Provider prompt caching can reuse matching prompt prefixes under provider-specific rules. | A local instruction cache is a different mechanism and cannot guarantee faster remote inference. |
| S9 | Speculative decoding uses draft proposals and target-model verification during decoding. | Model handoff over Chat Completions is not token-level speculative decoding. |
| S10 and S11 | llama-server caches prompts by default (cache_prompt true), accepts id_slot and a cache-reuse setting, and reports per-request timings (cache_n, prompt_n, predicted_n, prompt_ms, predicted_ms) and prompt_tokens_details.cached_tokens. | Read the counts (spec 0.31, section 6): an adapter default of 0 is not a measurement. Launch settings stay pinned (RM18). |

Selecting a skill means selecting and loading instructions into model context. It does not mean that the model executes a skill file as a program. A skill can suggest actions; only the gateway or a client tool executor performs them.

No universal speedup, cost saving, minimum RAM figure, or accuracy level is asserted. The selected GGUF file, actual hardware, provider location, context length, and tool latency materially affect results.

## 3 Components and ownership

| Component | Responsibility |
| --- | --- |
| API layer | Validate requests; expose the supported chat contract and native run API; authenticate callers. |
| Orchestrator | Own state transitions, budgets, routing, handoff, cancellation, and the final-answer owner. |
| Model adapter | Translate normalized messages, tools, and generation options into provider-specific requests and events. |
| Skill registry | Validate packages; expose descriptions; load selected instructions and approved resources. |
| Tool registry and executor | Validate arguments and permissions; execute registered functions; record outcomes. |
| Run store | Persist ordered events, tool outcomes, pending approvals, and versioned execution state in SQLite. |
| Demo UI | Display model decisions and execution evidence; collect clarification and confirmation; compare modes. |
| Selector | Propose a skill, a clarification, or nothing for a request from the advertised catalog, and optionally narrow the skill's tools; built in or out of process (RM28, spec 0.31). It executes nothing and grants nothing. |
| Placement policy | Decide, from recorded timing samples, where a generation runs, local, external, or not at all, and record the prediction (RM27, spec 0.31). It never changes a budget. |
| Asset catalog service (RM34, RM38, RM43) | Own provenance, safe metadata projections, catalog publication, eligibility, lexical index and source refresh; execute no asset. |
| Recommendation coordinator (RM35, RM36) | Own the v2 deadline, validation, fallback, admission, separate persistence and final provenance. |
| V2 primary selector (RM35, RM41) | Rank the offered catalog; the built-in hybrid owns embeddings/fusion. Execute nothing and grant nothing. |
| Optional adaptation stage (RM42) | Apply explicit bounded scoped feedback after primary validation and before final admission; retain base and final output. |
| Qualified host adapter (RM37, RM39) | Authenticate direct input and resolve exact assets for host-owned loading/use/approval. Production action/use and current snapshot integration remain blocked (section 7.6). |
| OpenClaw provider plugin | A separately packaged TypeScript plugin connects OpenClaw inference to the Python gateway over the existing client-owned chat API; OpenClaw retains sessions, tool execution, and approvals (RM33, section 7.5). |

The model produces proposals. The orchestrator decides whether a proposal is admissible. The executor owns side effects. The UI renders evidence; it does not infer hidden model reasoning. A selector proposes a skill; the gateway admits it (RM28). The placement policy decides where a generation runs and never changes a budget (RM27). Before external dispatch, operator-configured policy MUST permit sending the effective prompt and selected tool data to that endpoint. Credentials and fields classified local-only MUST never be included; if required evidence cannot be shared, return needs_external with the disclosure restriction.

The local gateway binds to loopback by default and requires a generated application token. Local inference also binds to loopback. External credentials remain server-side in environment variables or an OS credential store. Native Windows operation MUST NOT require WSL or Docker. The initial platform matrix is Apple Silicon macOS and x86-64 Windows; other architectures are optional qualification targets.

## 4 Execution requirements

### 4.1 Routing and local autonomy

**RM01** The default policy MUST be local-first where a local model is configured (a gateway without one runs managed external execution, RM26). A request successfully handled locally MUST cause zero external inference calls, including routing or validation calls. The trace MUST make this verifiable.

**RM02** Managed runs consume selection v1; recommendations alone consume v2 (section 4.6). The protocols are explicitly configured and never implicitly upgraded. In managed execution, a selector MUST select among an advertised skill catalog, and the gateway MUST produce a normalized routing decision from that selection (RM28). The built-in selectors are the local model's routing generation, the default, and a deterministic example matcher; the gateway, never the selector, produces the route, the reason code, the language, and the clarification for a missing identifier. Supported decisions are local, external, clarify, and parallel. Parallel is admissible only for an enabled fixed workflow. Unknown skills, invalid fields, or unavailable capabilities MUST NOT trigger tool execution. Client-owned tool mode uses capability and context checks without claiming managed skill selection.

**RM03** Local execution MUST be bounded. Initial defaults are one routing generation, up to three subsequent local generations, two executed tool calls, one format-repair generation within those limits, and a four-second active local budget including routing and tools. A model generation can return a tool proposal or a final answer. The limits are configuration values and MUST be recorded in each run.

**RM04** Before answer output is committed, escalation MUST occur on exhausted local budget, unrepaired output format, a skill marked external-required, unavailable local capability, oversized context, a local generation that the placement policy predicts over its limit or that misses its deadline (local_slow, RM27), or an explicit valid escalation proposal, provided external dispatch is permitted. Otherwise return needs_external. After output is committed, failure terminates the stream as specified in section 7.3. The trace MUST use a reason code. A model's self-reported confidence MUST NOT be treated as a calibrated probability or the sole routing safeguard.

In the MVP the only explicit escalation proposal is the routing decision route=external with reason code complex_skill (section 8), produced in the routing state. The external route with reason code parallel_workflow (section 4.4) is not a proposal: the gateway produces it when the selected skill's parallel workflow is not admissible, as one of the gateway-detected triggers above (unavailable capability). The local model has no escalation action during local_running, so there a stop comes only from the gateway-detected triggers above. A model-visible escalation action for local_running is out of scope for the prototype; if one is added later it is an internal control action and MUST NOT be exposed as an application tool (RM09).

**RM05** A task with missing required identifiers MUST request clarification. Resource names such as database IDs MUST come from the request, established conversation context, or tool results. The system MUST NOT invent an object identifier to make a tool call possible.

The router receives caller instructions, relevant conversation context, and compact skill descriptions. The 500 ms experiment limits this complete input to 2,048 tokens measured by the local tokenizer. Longer inputs bypass the fast experiment and go to the external path if permitted; they MUST NOT be silently truncated or counted as short-context successes. No full document or full tool history is loaded into the fast router by default.

**RM26** The gateway MUST operate without a usable local model, whether none is configured (absent), the configured one cannot run on this machine (unavailable), or it runs but too slowly to help (unsuitable), and it MUST detect the last two itself (spec 0.31). Detection runs at startup, after restart recovery, when placement.detect is true (section 14.1): the gateway checks that the runtime answers and that the model loaded within placement.warmup_seconds, which otherwise classifies the local model as unavailable, and that the routing-shaped warm-up generation of section 6 finishes within the local per-stage active budget (section 11), which otherwise classifies it as unsuitable (that generation is the first request after the model loaded, so the check measures it cold when the runtime has just started; a routing-shaped warm-up that fails, or that does not finish within placement.warmup_seconds when that is shorter than the stage budget, classifies the model unavailable; spec 0.37). With placement.detect_stages true (spec 0.48, section 14.4.7; false by default) the routing-shaped and skill-shaped warm-up generations must finish within that budget together, because a local stage needs at least one generation of each (the routing-shaped one alone decides when no skill-shaped request is sent); a skill-shaped warm-up that fails after a routing-shaped one that fits leaves the model ready, and one cut off by placement.warmup_seconds at or after the stage budget classifies it unsuitable; the launcher prints one line that names the class and the cause. Readiness repeats the availability check, so a local model that becomes available later is used from then on and one that stops answering is classified unavailable again (a model last measured unsuitable comes back unsuitable; spec 0.37), and the placement policy (RM27) keeps re-evaluating an unsuitable one from its samples, so the class is a measurement, never a permanent label. With placement.detect_stages true, while the gateway runs, a ready model is also classified unsuitable from the outcomes of its local stages (spec 0.48, section 14.4.7): when the three latest recorded local stages of that model all ran out of local time and the latest of them ended less than placement.probe_after_seconds ago. Once that latest stage is older, the model is ready again, so the next local stage measures it again, at a cost of at most one per-stage budget of one request per placement.probe_after_seconds, and a local stage that does not run out of time ends the streak. Stage outcomes are kept in the run store, so after a restart the rule applies as soon as the startup check finds the model ready. In the absent, unavailable, and unsuitable classes auto is managed external execution: the selector chain runs without a model call (the configured chain without model_router, or example_match alone when that leaves no selector; spec 0.37), the selected skill is loaded with its body and completion predicate, prefetch runs (RM29), the clarification for a missing identifier (RM05) and the confirmation for a mutation (RM11) apply, and every generation runs on the external model; when no selector chooses a skill, the run hands off with the catalog as section 4.4 describes. When the class is absent or unavailable, local_only and parallel_demo are not permitted; when it is unsuitable, local_only remains permitted under operator policy and runs locally within its budgets, while parallel_demo is not permitted (section 7.4). Readiness and the demo UI report the class and cause. run.accepted records the configured local model_id for unavailable and unsuitable, and local_model null only for absent; only absent is shown as no local model configured (sections 7.4, 8, 9, 14.1). An auto route that uses managed external execution for one of these classes records reason code no_local_model and its cause (absent, unavailable, or unsuitable) on route.selected as local_model_status (section 8); every run records its class as local_model_status in run.accepted (section 8), never as a failed local model mid-run, which stays capability_missing under degraded mode (section 11) for a local model that was usable and then failed. With placement.detect false, an unavailable local model is only reported not ready, as before this revision. external_only is unchanged by this revision, so it remains the comparison baseline of sections 9 and 12.

**RM27** Where a local model is configured and an external path exists, the gateway MUST decide per generation where it runs from recorded timing samples of this machine, never from an assumption that local inference is faster or slower (spec 0.31). The gateway keeps, in the run store, a timing sample for every generation it makes (model, purpose, input tokens, cached tokens, first-token time, total time, output tokens) and for the startup warm-up and the idle probe (section 6); external samples come from every external call, so a handoff measures the external path for free. Before a local generation the policy predicts its time from the measured input tokens, the expected output for its purpose, and the sample throughput (with the warm or cold prefix that the last sample showed), and records the prediction. The rules are these. The hard cap: a generation predicted not to fit the remaining per-stage budget does not start; the budget itself never moves, and an operator who wants more local time on a slow machine raises active_seconds in the budgets table of the launch file (section 14.1), which the run records (RM03). The deadline: a local generation that starts gets a deadline of its prediction times placement.margin, capped by the remaining stage budget; a miss cancels the generation, keeps its evidence, and escalates with local_slow (RM04). The idle probe: a local estimate older than placement.probe_after_seconds is refreshed, while no run is active, by one warm-up-shaped generation recorded as a sample labeled probe (section 6); a user's request is never spent on it. The expected-wait rule, only under the experimental policy expected_wait: when the store holds external samples and local outcomes of the selected skill on this model (its completed and escalated local runs), a generation runs locally only when its predicted time is below the skill's observed local success rate times the expected external time (the median external call time of the samples times the external generations the skill's recorded external runs have needed, at least one); it is an experiment because the success rate measures the model's quality on the skill as much as the device, and its runs are labeled and reported apart like the routing cache (section 12). A stop under these rules hands the skill stage off with the selected skill and reason code local_slow, so its body and completion predicate travel with it (RM13). In local_only the policy records predictions and skips nothing, because no external path exists; the per-stage budget still bounds the stage. Routing stays local when it fits (a short output and a cacheable prefix, section 10); a slow machine on which the routing generation does not fit uses a chain that starts with the deterministic selector (section 14.1) and, when that is unsure, the catalog handoff of section 4.4, never an extra external routing generation, because one costs more than the local stage budget it would save. The policy is placement.policy in the launch file: local_first, the default and the baseline of section 12, which records predictions and applies no rule; device_aware, which applies the hard cap, the deadline, and the idle probe; or expected_wait, which adds the expected-wait rule (section 14.1). A later revision decides from the section 12 runs whether device_aware becomes the default (section 12.3). A prediction is labeled as one and recorded next to the actual duration (section 8); predicted time, actual time, and wasted local time are metrics of section 12.1.

**RM28** Skill selection MUST go through one published interface, so that a third-party system can replace it by configuration (spec 0.31): a SelectionRequest (schema_version 1: run_id, the redacted conversation, the run language, the effective execution mode, the catalog of offered skills with id, version, content hash, description, languages, local eligibility, allowed tools, and example requests, the caller's permissions, and a deadline) and a SelectionResult (schema_version 1: a candidate of kind skill, clarify, or none, with the skill id or the clarification text; an optional tools list that narrows the selected skill's allowed tools; a mechanism label; a selector-reported confidence that is never a calibrated probability (RM04); an optional alternatives list of the other skill ids the selector judges relevant to the request, which the gateway ignores for admission and the selection benchmarks count in the predicted set (section 12.4); the selector's name and version; and the model calls the selector reports having made). A selector proposes; the gateway admits: it validates the result against the schema (a result that names another selector, or claims a mechanism label of the gateway (section 8) or of another built-in selector, is an error; spec 0.36), checks catalog membership and admissibility under the mode and the policy, runs the RM05 identifier check and asks the clarification itself, intersects the narrowing with the allowlist (narrowing can only remove tools, RM08), builds the RouteDecision, and records route.selected with the selector's name, mechanism, elapsed time, and every selector tried (section 8). A selector executes nothing, grants nothing, and changes no budget. The built-in selectors are model_router (the local model's routing generation of this section; the default chain is this selector alone, which is the baseline) and example_match (deterministic matching of the request against the offered skills' example requests and descriptions in both languages with identifiers masked, returning the best skill and the margin to the second, or none under selection.example_match_score and selection.example_match_margin (section 14.1); no model call; its accuracy is measured in section 12 and never assumed). A third-party selector runs out of process, as a loopback HTTP endpoint speaking the two JSON shapes; an endpoint outside loopback is refused at startup, because the request text would leave the machine (section 3). The contract is one HTTP POST to the configured URL with the SelectionRequest as the JSON body and a 200 response with the SelectionResult as the JSON body; any other status, an unparsable body, or no response within selection.timeout_seconds is an error that falls through. The two schemas are published as selection_request.v1.json and selection_result.v1.json next to the gateway's other versioned schemas (section 8), so a third party implements the endpoint against them without reading gateway code. An operator of a slow machine, or of a gateway without a local model, puts example_match first in the chain (section 14.1); a later revision decides from the section 12.4 runs whether the default chain changes. The chain is tried in the configured order; a result of none, a timeout (section 11), an error, or an inadmissible result falls through to the next selector and is recorded; when the chain ends with nothing, the run hands off with the catalog when external dispatch is permitted (reason code selection_failed; invalid_output when the model router's output was rejected; local_slow when the placement policy did not run the model router's generation, RM27) and otherwise ends as needs_external. With selection_failed the gateway first records its own decision (route external, skill_id null, reason selection_failed) in route.selected with mechanism selector_chain and every selector tried; a rejected model router output records no route.selected and escalates with invalid_output, as before this revision (spec 0.36). Model calls that an out-of-process selector makes on its own are outside the trace: the self-report is recorded as a claim, and evaluation reports such runs in their own column (section 12.2). RouteDecision keeps schema version 1.

### 4.2 Skills and instruction loading

**RM06** A skill MUST have a stable name, description, version, content hash, and an instruction body. The model selects the skill by name. The gateway then loads its body and the permitted tool schemas. Every load MUST emit a skill.loaded event containing the name, version, and hash.

The package uses SKILL.md with Agent Skills name and description frontmatter. RelayMind-specific settings live in a separate registry manifest: version, supported languages, local eligibility, allowed tool IDs, resource paths, completion predicate ID, optional parallel_workflow ID for the fixed parallel workflow (RM15), and optional prefetch declarations (RM29). Completion predicates are registered gateway validators, not executable text supplied by the model. This is a documented RelayMind extension, not a claim of complete compatibility with every skill host. [S7]

The registry manifest is the file `skill.manifest.json` in the package directory, next to SKILL.md. It is a JSON object with a `schema_version` field, following the `*.manifest.json` convention of the model artifact manifests in section 6. The skill's content hash covers both files.

Skill locations are operator configuration, not code. The registry loads from an ordered list of skill roots. The default list is `["skills/"]`, the `skills/` directory of the checkout. An operator MAY replace the list, for example with a single isolated directory in a container or a test fixture, or extend it with further local directories such as a team-shared folder; a configured list replaces the default, it does not add to it. Each root is scanned one level deep, and every subdirectory of a root is a candidate package. A candidate that lacks SKILL.md or `skill.manifest.json`, or whose files fail validation, is a startup error, never skipped silently. Plain files in a root, such as a README, are ignored. Skill names MUST be unique across all roots; a duplicate is a configuration error, not a precedence rule. Each run records the configured roots and the skill catalog offered to the router in the run.accepted payload (section 8); this is the version snapshot that RM07 preserves. Roots are local filesystem paths. Fetching packages from a URL or a remote registry is automatic skill installation, which section 1 leaves out of the prototype.

The MVP uses at most eight short skill descriptions per router prompt and one selected skill body at a time. Resource reads are restricted to the selected package directory. Skills cannot install dependencies, execute bundled scripts, change permissions, or alter model configuration. Any required executable operation must be an explicitly registered tool.

**RM07** Updating a skill or its tool schema MUST change its version or content hash and invalidate dependent routing-cache entries. Existing runs retain their original version snapshot; a required missing version causes an explicit failure rather than silent substitution.

**RM29** A skill manifest MAY declare prefetch calls (spec 0.31): a read-only registered tool from its allowlist and, for each required argument, either an identifier the gateway resolves from the request by the RM05 rule (exactly one allowed value appears in a user turn; otherwise the call is not prefetched and the model proposes it as before) or a documented constant for an argument that is not an identifier. When performance.prefetch is true (section 14.1; false, the default and the baseline, keeps the declarations idle), the gateway executes the resolved calls before the first skill generation, concurrently, through the executor with every check of a model proposal (RM08 to RM10), records tool.proposed with actor gateway and mechanism prefetch (section 8), and puts the results into the conversation as tool exchanges, so the skill stage starts with its evidence and tool output stays data (RM12); each prefetch call counts toward the entire-run tool limit and, when the skill runs locally, toward the per-stage tool limit of its first stage (section 11); when the resolved calls that need a new execution exceed the room the tool budget has left (one execution for each, as for an admitted set, section 4.3), none of them is started or recorded, and the model proposes them as before (spec 0.34). The budgets are launch configuration, not part of a manifest, so the declarations are checked against them at startup, after the registry has loaded and before any run, and only when performance.prefetch is true: a skill whose declared prefetch calls alone exceed the entire-run tool limit, or, for a skill not marked external-required, the per-stage tool limit, stops startup with an error that names the skill and the limit; with prefetch false the declarations are idle and are not checked against the budgets (spec 0.34; 0.31 to 0.33 called this a manifest validation error at load). When nothing is pending after prefetch, that is, every tool the stage offers has a succeeded result in the run (spec 0.34), the first skill generation is an answer generation (section 7.3). A skill that routes external with its skill ID (a complex skill, or managed external execution, RM26) has its first skill stage in the external stage, so its declared calls run after handoff.started and before the first external generation (spec 0.37). At load time the registry validates the declared bindings, without a request: the tool must be read-only and in the allowlist, every required argument must have a binding to a registered identifier parameter or a documented non-identifier constant, and parameter names and constants must satisfy the tool schema. The constants are checked against the tool's full schema, its required properties and any rule that ties properties together included, once for every combination of the allowed values the request-bound identifiers can take, so the RM09 check at run time never refuses a declared call for its constants (spec 0.34); the same call declared twice is also an error, because both would run as one operation. A violation is a manifest validation error. At run time the gateway resolves identifier bindings from the request under RM05; a missing or ambiguous identifier skips that prefetch call, not the skill, and is not a manifest error. The ordinary clarification and model-proposal checks still apply. Prefetch runs before any model generation of its stage, so it does not move dispatch authority (RM14), and its operations are completed operations of the run like any other, so a later proposal of the same call replays the recorded result (RM10). run.accepted records prefetch as the boolean option and prefetch_declarations as the offered skills' declarations (section 8); prefetch is a labeled configuration in evaluation (section 12.2).

### 4.3 Tools and execution boundaries

**RM08** Registered tools MUST declare a name, input schema, output schema, execution timeout, side-effect classification, handler, and authorization rule. Tool availability is the intersection of the skill allowlist, operator policy, and caller permissions. Names in a client-supplied tools array do not register executable handlers.

**RM09** The gateway MUST validate the full tool name and arguments before execution, reject undeclared fields where the schema disallows them, and validate returned data. Partial streamed argument JSON MUST never execute. Internal control actions such as skill selection and escalation MUST NOT be exposed as ordinary application tools.

Admitted calls per generation (spec 0.31). A generation may propose several tool calls. When performance.calls_per_generation is many (section 14.1; one, the default and the baseline, keeps the one-call rule of earlier revisions), up to the per-stage tool limit (section 11) of read-only calls are admitted from one generation in a local stage, and up to the remaining entire-run tool limit in the external stage, where the per-stage limits do not apply: each is validated on its own (RM05, RM09), executed through the executor in proposal order, and answered as its own tool message, so a model that plans several reads does not spend a round trip on each. A mutating call is admitted only as the generation's single call, because the confirmation binds one call (RM11); a generation that proposes a mutating call together with others, or more calls than the limit, is rejected back to the model as data with code multiple_tool_calls, as every generation with more than one call was before this revision. When any call of an admissible set fails its own validation, no call of the generation executes and the first rejection goes back to the model as data, using the format repair of section 11, so a partly valid set never runs in part. That rejection belongs to the call that failed its own validation: it answers that call and is recorded on its tool.proposed, and every other call of the set is answered and recorded as not executed (code not_executed), so a valid call is never reported as malformed. A set within the limit is also rejected as a whole before anything runs, with code multiple_tool_calls, when the tool budget has no room left for it (spec 0.34): the room is what the per-stage and the entire-run tool limits have left in a local stage, whichever is less, and what the entire-run tool limit has left in the external stage; the set needs one execution for each call that needs one, so a call that repeats a completed operation is a replay and needs none (RM10), while the limit on the number of calls counts every proposed call. A rejection about the set (more calls than the limit, a mutating call among others, or no room in the tool budget) belongs to no single call, so it is recorded on the tool.proposed of every call and answers every call (spec 0.34). Either way the rejection of a set is one exchange that answers every proposed call, one assistant message that holds every call and then one tool message for each, in proposal order, and each tool message carries the rejection that the trace records for that call, so the trace and the conversation agree (RM16, RM22). A retry (section 11) is not reserved for, so a retry can still use the last of the budget in the middle of a set, and the run then ends on budget as it would for a single call; an exhausted time limit can also stop a set in the middle, because time is not predicted. An admitted set runs in proposal order, one call after another (spec 0.34): when a call of the local actor fails, the stage escalates with reason code tool_failure at once, as for a single call (section 11), and the later calls of the set do not run; the external actor gets every result of the set, a failed one included, as data and continues. Under one, a generation with more than one call is rejected as before: every call is recorded with multiple_tool_calls, and the exchange holds the first call and the rejection only. The client-owned alias keeps its one-call rule (section 7.2), and so does the local_health branch of the fixed parallel workflow under either value (section 4.4, RM15; spec 0.34).

**RM10** The executor MUST persist a logical operation ID before a side effect. Replays use the recorded result for that operation. A changed argument set is a new proposal and requires revalidation. A timed-out write with an unknown outcome MUST be marked unknown_outcome and MUST NOT be retried automatically. This provides controlled deduplication; it does not claim universal exactly-once delivery to external services.

**RM11** Mutating demo actions MUST require confirmation tied to the run, tool, canonical arguments, target, and current state version. Confirmation expires after five minutes and is single-use. Changing the target or arguments invalidates it. A textual yes in unrelated chat history is insufficient authorization.

Confirmation flow. A registered mutating tool declares the required input argument that names its target (confirmation_target, for example database_id); a mutating tool without one cannot be confirmed, so the gateway rejects its proposals back to the model as data. A proposal of a mutating tool passes the same checks as any proposal (RM05, RM08, RM09) and is then not executed. The gateway moves the run to waiting_confirmation, issues a random single-use token, stores only its SHA-256 hash with the approval (section 5), and records confirmation.required (section 8). The plaintext token is returned once to the caller that started or resumed the run and is never written to the store, the trace, or a log. A target under a configured secret field is redacted like the arguments (RM12). The approval binds the run, the tool, the canonical arguments (which include the fixture revision for a deletion, section 9), the target, and the run's state version in waiting_confirmation. Only a resume that presents the approval ID and the token, with the run at that version, can use it, and a use of it, approving or denying, consumes it. A proposal for different arguments or another target is a new proposal and needs its own confirmation. A proposal that repeats an operation of the run that already has a recorded outcome gets that outcome and asks for no confirmation, because it runs no handler (RM10). The sandbox handler still compares expected_revision atomically (section 9), so a fixture that changed after the proposal is a conflict with no mutation.

**RM12** Tool output is data and MUST NOT override gateway rules or grant new tool permissions. The prototype MUST test malicious instructions embedded in tool output. Logs and traces MUST redact configured secret fields.

### 4.4 Handoff, workflows, and parallel operation

**RM13** Handoff MUST preserve the original user request, applicable caller instructions, selected skill version, structured tool results, completed operation IDs, pending work, permitted tools, language, and remaining budget. Both models use the same logical tool registry. Local hidden reasoning, KV cache, and model-specific token IDs are not transferred.

Handoff creates a new external request using normalized messages and evidence. Local assumptions are identified as proposals, never recast as tool facts. If evidence exceeds the external context budget, the run fails with context_limit_exceeded unless a skill defines a tested bounded evidence-selection method. The MVP does not silently summarize away evidence or permissions.

The gateway builds the envelope from the run's recorded state, not from model memory. The tool operations in the run store supply the completed operation IDs and the structured results, each with its source reference and truncation flag. Rejected local tool proposals and rejected local draft answers go in a separate local_proposals list, and every entry is labeled as a proposal. Pending work lists the permitted tools of the selected skill that have no completed operation, then the final answer. The envelope is sent as normalized messages: the gateway rules and the envelope fields that are not tool output in a system message, which orders the parts from the one that never changes to the one that changes with the run (spec 0.35): the rules, the skill instructions, the fixed completion criteria (below), the skill catalog when no skill was selected, the answer instruction, and last the handoff JSON with the run ID and the remaining budgets; then the original conversation, then each completed operation as a tool call with its tool result message, so tool output stays data (RM12).

Before dispatch the gateway measures the whole external request, messages and tool schemas, against the context limit of the external adapter. It uses the adapter's tokenizer when it has one. Otherwise it uses the UTF-8 byte length of the request, which is an upper bound on the token count, so a request that does not fit is never passed. A request over the limit ends the run as failed with error code context_limit_exceeded and reason code context_limit, before any external call. The same check runs again before every external generation, because tool results accumulate. Handoff needs external dispatch to be permitted: an effective execution mode other than local_only, a configured external model, and room in the entire-run limits. Otherwise the run ends as needs_external (RM04). A tool operation of the run that is still in flight, or that ended unknown_outcome, blocks handoff (RM14): the run ends as needs_external with reason code tool_failure, and the partial evidence stays in the trace. A stop that the external stage could not resolve either does not hand off: a selected skill none of whose allowed tools is permitted to the caller (RM08). The run ends as needs_external with reason code capability_missing and makes no external call. One more stop ends without a handoff. An admitted route=parallel is never handed to one external actor in place of the workflow: it runs the parallel workflow (RM15, below). An unavailable local model, a missing local capability or a failed local generation, ends as needs_external with reason code capability_missing, unless the operator policy permits degraded mode (section 11), in which case it hands off like any other stop.

The external stage. On handoff the run enters external_running and records handoff.started. From then on the local actor holds no dispatch authority and cannot publish the final answer (RM14). The external model may propose tools from the envelope's allowed tools. The gateway validates each proposal (RM09), checks identifier provenance (RM05), and runs it through the same executor as a local proposal. A proposal that repeats a completed operation, the same tool with the same canonical arguments, gets the recorded result and runs no handler (RM10). A mutating tool proposed in the external stage goes through the same confirmation flow as a local proposal (RM11, section 5): the run suspends in waiting_confirmation from external_running, and an approved resume returns it to external_running. When a skill is selected, the external answer must meet its completion predicate. The answer is buffered, validated, and then published as answer.delta by the external model (except eligible live answer generations under section 7.3.1), which is then the final-answer model (RM16, RM20). External generations are limited by external_generations (default 6) and by external_seconds for each generation (default 30, section 11), inside the entire-run limits. The per-stage local limits do not apply to the external stage. When no skill was selected, for example in external_only, the envelope carries skill null, the external model gets the skill catalog descriptions and the permitted tools of the offered skills, and the external model does not load a skill body in this version.

Completion criteria in the external request (spec 0.31; detail spec 0.35). The external request states the selected skill's completion criteria explicitly, generated from the registered predicate, so the external model is told what the gateway will check; the criteria are gateway rules, not tool output (RM12). They have two parts. The fixed part (the section labels it must use, the patterns it must not contain, and what to keep exactly, such as the status word) is the same for every run of a skill and sits in the first system message after the skill instructions. The value part (the exact values the answer must preserve) is a gateway rules system message placed at the end of the conversation before each external generation once a successful result exists; it replaces its earlier copy instead of adding another, and it is part of the request measured against the context limit (RM13). Its values come only from schema-typed fields of the latest successful tool result (an enum, a timestamp, an identifier of plain token shape, a count, a boolean), never from free text, so injected text in a tool result cannot reach it. A correction after a rejected answer names the checks the answer failed, in gateway text that does not quote the answer; the local correction is unchanged. The synthesis request of the parallel workflow keeps its own instruction and its generic correction and gets no criteria message (AC14). The reason is finding F6 of the 2026-10-23 analysis in `docs/EVIDENCE.md`: on the external path the predicate's rejections each cost a correction round trip. Corrections per completed run is a metric of section 12.1, reported before and after this change.

**RM14** Only one actor may dispatch a given logical tool operation or publish the final answer. Escalation revokes the local actor's dispatch authority. Late results may be retained as evidence, but cannot trigger additional local side effects. In-flight writes with uncertain outcomes block automatic continuation that could repeat them.

**RM15** Parallel mode MUST initially support one trusted workflow with independent read-only branches. For example, the local branch collects current health while the external branch drafts a diagnostic checklist from the user request. The external draft is provisional; after both branches finish, a new external call combines the observations and checklist. The extra call and its latency MUST be measured.

A running Chat Completions generation is not assumed to accept injected tool results. The implementation either waits for dependencies before starting it or makes a subsequent request. The default local-first route does not launch an external model merely to hide latency.

The parallel workflow is enabled by operator configuration, which names the enabled workflow ID; a skill joins it by declaring that ID as the parallel-workflow ID in its registry manifest (section 4.2). Both are required. route=parallel is admissible only when the run's effective execution mode is parallel_demo, or auto where operator policy explicitly allows the workflow in auto; by default auto does not run it, because the workflow ends in an external synthesis call and the local-first route does not launch an external model to hide latency. local_only and external_only never produce route=parallel. When the selected skill declares a parallel-workflow ID that configuration or the effective mode does not admit, the gateway routes it external with reason code parallel_workflow, and local_only then returns needs_external (section 7.4). The gateway produces that decision itself from the manifest, the configuration, and the effective mode, like the other gateway-produced decisions in section 8; the model's contribution is the skill selection (RM02), not the choice between parallel and external. A decision that reaches the validator with route=parallel in a mode or configuration that does not admit the workflow is therefore invalid output (section 8), never a parallel_workflow escalation. In parallel_demo a run whose configured workflow is unavailable, because configuration enables no workflow or the external endpoint the workflow needs is not available, ends as failed with error code workflow_unavailable; the compatible chat endpoint reports it as HTTP 503 with that code, as for an unavailable required model (section 11). The gateway checks both causes before the routing generation, with reason code parallel_workflow in run.failed, so no model is called for a run that cannot succeed; it ends the run the same way when the run routes external with reason parallel_workflow in parallel_demo, because the selected skill declares a workflow that configuration does not enable. A run that routes parallel runs the workflow in parallel_demo, and in auto when operator policy admits it. The other modes keep their rules above: auto hands such a run off or, in local_only, returns needs_external.

The workflow run (spec 0.25, #30). A run that routes parallel loads the selected skill (skill.loaded, RM06), checks that a tool of the skill is permitted to the caller (RM08; otherwise the run ends as needs_external with reason code capability_missing and makes no external call), and moves from routing to parallel_running. It then starts two independent branches together. Each model call and tool event of a branch carries its branch name (section 8), so every step is attributable.

- local_health. The local model runs a skill-stage generation with the skill's read-only tools offered. Its tool proposal passes the same checks as any proposal (RM05, RM09) and runs through the executor (RM10, RM14); a proposal of a mutating tool is rejected back to the model as data, because the workflow's branches are read-only. The branch ends with the tool result and writes no answer. It uses the local per-stage limits (section 11), including the one format-repair generation. It makes one tool call under either value of performance.calls_per_generation (spec 0.34): a generation with more than one call is rejected back to the model with code multiple_tool_calls through that repair, as under one (section 4.3), because the branch ends with one tool result. A health service that reports unavailable is a successful observation (section 9) and travels to the join unchanged.
- external_checklist. The external model runs one generation with no tools. Its input is the original conversation and an instruction to draft a diagnostic checklist from the request alone, with no claim about observed health and no claim from logs. The output is a provisional draft: it is not tool evidence and is never published as the answer. The generation has the purpose draft, counts as an external generation (external_generations) and in the entire-run generation limit, and is bounded by external_seconds.

The branches never see each other. No result is injected into a running generation (RM15): the branches finish, and a new request combines them. The workflow needs the local branch generation and two external generations, the draft and the synthesis. A run whose entire-run generation limit or external_generations leaves no room for them, or whose entire-run time is spent, ends as needs_external with the budget named in dispatch_blocked, before any branch starts. The draft request is measured against the external context limit before the run moves to parallel_running, so no branch starts for a run whose draft cannot be sent. If a branch fails, the other is cancelled, in the way of a run cancel: the adapter of its generation is asked to cancel, its in-flight work stops, and its model call ends with the error code cancelled. The calls of both branches stay in the model_calls inventory of the terminal event and in external_calls, abandoned ones included (section 12.1). A local branch stop ends the run as failed with needs_external and the RM04 reason code of the stop (local_budget, invalid_output, tool_failure, or capability_missing), without a handoff. A failed or exhausted external branch ends the run as failed with external_failed and reason code parallel_workflow. A blank draft, or a draft that proposes a tool call, is a failed external branch. An external request over the context limit ends the run as context_limit_exceeded (RM13).

The join. When both branches have finished, the gateway checks again that the entire-run limits leave room for the synthesis and that no tool operation of the run lacks a known outcome; otherwise the run ends as needs_external with reason code parallel_workflow (with the budget named in dispatch_blocked, or reason code tool_failure for the operation), without a handoff. It then measures the synthesis request against the external context limit, records handoff.started with reason code parallel_workflow, the external model, the skill, the operation IDs of the tool results, no allowed tools, the measured request, and the workflow ID, moves the run from parallel_running to external_running, and revokes the local actor's dispatch authority (RM14). Final ownership transfers here and never earlier: no answer.delta is written before the join (RM20). The synthesis is a new external generation with the purpose external, the branch name synthesis, and no tools. Its request has the gateway rules, the skill instructions, the original conversation, the health tool result as a tool exchange, and the draft, labeled as an unverified provisional draft that was written from the request alone and is not log-backed. The draft is untrusted model text: it travels in a user-role data message, JSON-encoded, never in a system message. Tool output and the draft are data and never change the rules (RM12). The answer is buffered, must meet the skill's completion predicate, which keeps the exact returned status and checked_at and the draft label, and is then published by the external model, which is the final-answer model (RM16, RM20). A rejected answer gets a correction request inside external_generations. A synthesis that cannot finish ends the run as external_failed with reason code parallel_workflow.

Provenance (RM16). The answer states the health observation exactly as returned, including an unavailable status, and labels the checklist as a draft that is not a diagnosis supported by logs. The completion predicate health_checklist_separated enforces both.

Cancel and restart. A cancel request, native or by a chat disconnect, stops both branches and the synthesis call as it stops a single run: the adapter of every generation in flight is asked to cancel, every in-flight tool operation is settled, and the run ends as cancelled with all its model calls in the inventory. Restart recovery ends a run that was in parallel_running, or in external_running during the synthesis, as failed with interrupted (section 5); its pending read-only operation is settled as failed, its tool.finished keeps the branch of the operation's tool.started, and model_calls is rebuilt from model.started events, branch calls included. The interrupted run.failed has no workflow object: the monotonic figures ended with the process, and the gateway does not estimate them.

Measurement (RM15, RM25). A run that started the workflow reports a workflow object in its run.completed, run.failed, and run.cancelled payloads (section 8), except the run.failed of restart recovery: the workflow ID, the elapsed time of each branch and of the parallel stage, the extra call latency (the duration of the synthesis calls), and the abandoned calls (the parallel branch calls that ended cancelled; a synthesis call is not one). The extra call latency is the added cost of the second external call; the gateway does not claim a saving against a sequential run it did not measure.

**RM16** A completed run MUST identify the final-answer model and every actual model call. Data provenance MUST be preserved: an unavailable health service cannot be reported as healthy, and a drafted checklist cannot be reported as a diagnosis supported by logs.

**RM30** Retired in spec 0.47 before implementation of the declarative workflow runner. YAML workflow packages, the skill manifest workflow key, workflow roots, and their plan benchmark are no longer deliverables. This identifier is reserved for historical references and MUST NOT be reused. The implemented fixed parallel workflow remains governed by RM15 and AC14. OpenClaw integration is RM33, section 7.5.

### 4.6 M10 catalog and recommendation selection (spec 0.51)

**RM34** The gateway MUST maintain a versioned provenance-backed catalog, atomically publish revisions, normalize bounded untrusted metadata without executing assets, preserve source-namespaced identities, distinguish relevance from availability, and invalidate changed/deleted assets. No metadata, selector or prefetch declaration grants execution permission (RM08–RM12, RM28).

All M10 objects below are closed: required fields are present, nullable means explicit null, optional fields are named explicitly, unknown fields are rejected. Versions are exact integers, booleans are not integers/numbers, numbers are finite, revisions are nonnegative integers, timestamps are UTC RFC3339. Hashes are lowercase 64-hex SHA-256. Structured hashes use canonical JSON (RM07); original content hashes use original bytes before redaction/normalization. Text/count/transport limits are authoritative in section 14.5. These conventions also apply to sections 7.6 and 8.1.

`AssetRecordV1` has required fields `schema_version:1`, `asset_id`, `kind:skill|mcp_tool`, `source_id`, `source_locator`, `source_version:string|null`, `captured_at`, `content_hash`, `description`, `language_tags`, `dependencies`, `availability:available|needs_setup|unavailable|unknown`, `stale:boolean`, and `identity`. IDs/locators/descriptions are nonempty strings; language_tags and dependencies are unique arrays of strings. `identity` is a closed discriminated union: a skill has `package_id` and `package_version:string|null`; an MCP tool has genuine `server_id`, original `tool_name`, exact `exposed_name`, full host-exposed `input_schema` JSON object and its canonical `schema_hash`. Other-kind fields are rejected. The input_schema must be a valid JSON Schema with references resolvable locally or to published meta-schemas under the existing section 7.1 boundary; catalog validation never fetches references. A valid schema hash is recomputed, never trusted from a label. No source credentials, headers or environment values occur in records. MCP provenance MUST be captured from a genuine declared source/host mapping; splitting an exposed name on `__` is not proof.

Asset IDs are opaque operator-source-namespaced identities, not display names. Same names in different sources remain distinct. A changed record retains its stable ID and changes content/version. Identical reimport is a no-op. Publication increments `catalog_revision` monotonically once for a changed committed generation; queries pin one revision. Explicit removal invalidates new selection immediately. Failed/incomplete fetch never implies removal. Source IDs/identity mappings are operator-owned. Imported fixtures prove their declared source provenance, never current host availability.

The searchable projection is separate from original bytes. It uses Unicode NFC and rejects prohibited C0/C1 control characters other than tab/newline/carriage return, HTML-like markup tokens (a `<` followed by an ASCII letter, `!`, `?` or `/`), malformed encoding, oversized fields, and the repeated-line case in section 14.5. It does not execute scripts, templates or package instructions. Display escapes text and labels excerpts as source data. Invalid records have explicit rejection reasons and exclusion counts; rejected/truncated coverage cannot be called complete. Local directory reads and reviewed metadata imports are supported core inputs. Opaque archives may be retained within acquisition bounds; arbitrary ZIP extraction is outside this contract. A safe package format with path/entry/uncompressed limits requires its own normative contract before inspection is implemented.

#### 4.6.1 Metadata imports and ordinary local skill directories

`AssetMetadataImportV1` is the closed input document for metadata_import sources, not AssetCatalogSnapshotV1. Required fields are `{schema_version:1,source_id,source_version:string|null,captured_at,complete:boolean,records,removed_asset_ids}`. `records` is an array of closed `AssetMetadataEntryV1` objects `{record,original_path}`. Each record is a closed `AssetMetadataRecordV1` with exactly `asset_id`, `kind`, `source_locator`, `source_version`, `captured_at`, `content_hash`, `description`, `language_tags`, `dependencies` and `identity`, obeying AssetRecordV1's bounds and kind-specific identity. Records cannot supply schema_version, source_id, availability, stale or gateway catalog/publication fields. removed_asset_ids is a unique bounded-ID array. No source credentials or host snapshot input is added.

metadata_import.path names one regular UTF-8 JSON file containing exactly one such object; relative source paths resolve from the launch configuration file's directory. The file's parent is the capture root. Root source_id must match the configured source, and no source may upsert/remove another source's IDs. Duplicate record/removal IDs or an ID in both lists reject the whole document. original_path is a normalized relative POSIX path: no empty/dot/dot-dot segments, absolute/drive prefix or backslash. Reject symlink components, root escapes, nonregular originals and aliases of the import file. source_locator is recorded, never fetched. Read boundedly into a stable staged capture once, hash/check those actual staged bytes, then publish from that capture without rereading mutable paths.

Recompute each original file's SHA-256 and require record.content_hash equality, separately from NFC/redacted projection hashes. An opaque archive may be hash-verified but never unpacked or indexed as instructions. This import indexes the admitted metadata/searchable fields only, not implicit full skill bodies. Recompute MCP canonical schema_hash and validate the existing local-reference rules. Preserve original import bytes/digest as source-generation evidence: source snapshot content_hash hashes those bytes, while source_version/captured_at come from the root and assets retain their record versions/captures. Successful output adds schema_version=1 and the configured source_id, with availability=unknown and stale=false for current imported records. There is no arbitrary status/evidence field; separately qualified source evidence is needed for other status paths. These checks prove byte/declaration consistency, not rights, source language, arbitrary assertion authenticity, live availability or Matrix export compatibility.

complete=false is an explicit partial batch: removed_asset_ids must be [], valid staged upserts commit atomically, omitted records remain, and source complete=false even if a prior generation was complete. Retained records the batch omits are marked stale=true, because a partial batch cannot certify them current; only records the batch carries get stale=false. complete=true declares the intended whole configured source inventory. Validate all records first; any rejected record fails the whole document, retains the prior generation and applies no removals, with exclusions/rejected counts and no uncommitted accepted-count claim. Omission never deletes: each intended deletion requires a supplied tombstone in removed_asset_ids. A tombstone must name an existing source-owned record, or a previously recorded removal by that same source (idempotent no-op); unknown/out-of-source removal is invalid. A declared complete inventory omitting a retained record without a tombstone is rejected as incomplete. Empty complete documents are valid only for an empty source or with explicit tombstones for every retained record. Commit upserts/removals in one revision transaction and invalidate changed/deleted eligibility; identical document/staged-original digests are a no-op. Any invalid record, integrity/path/bound failure or incomplete fetch rejects the whole import document (including partial batches), with no metadata change/removal; record exact exclusions and retain the last usable generation.

local_directory.path is a regular nonsymlink directory, resolved against the launch configuration directory. It MUST read ordinary installed/downloaded SKILL.md folders without requiring metadata-import conversion or a managed registry manifest. If a SKILL.md entry exists at the root (even invalid/symlink), treat root as one candidate with relative package key `.` and validate it; invalid root entry never triggers child fallback. Otherwise inspect immediate child directories only, sorted by UTF-8 relative name, selecting those with a SKILL.md entry. Do not recurse or follow symlinks; explicitly configured nested directories can be separate sources. A child lacking SKILL.md is not a package. Reject symlink root/candidate/SKILL.md/optional-manifest paths and any escape from the root/package. Enumeration/package limits in section 14.5 abort incomplete scans, rather than silently dropping later entries.

Read and stage original SKILL.md bytes once under section 14.5's original/frontmatter/body limits. Require UTF-8, opening line `---`, a later closing line `---`, a YAML mapping with nonblank string name/description, and nonempty instruction body. Parse data-only scalars/sequences/mappings; reject duplicate keys, explicit object/custom tags, anchors/aliases, excessive nesting and malformed types. Apply M10 name/description/control/markup/repetition bounds to the projection; do not require managed-v1 lowercase names or directory-name equality. Other frontmatter keys remain only in original bytes and cannot grant permissions or trigger script/resource reads. Do not call the managed registry's executable-package admission loader for arbitrary folders.

Optional frontmatter metadata must be a mapping if present. Recognized keys are version (nonblank bounded string), languages (unique language-tag array) and dependencies (unique bounded identifier array). Invalid recognized values reject the package. Missing keys yield null version/empty arrays, meaning unknown/not supplied, never proof of no prerequisites or English. No model guesses language or version. A regular nonsymlink optional skill.manifest.json may fill only missing version/languages using its section 4.2 keys after bounded strict JSON-object parsing. Frontmatter takes precedence; malformed JSON or invalid recognized fallback fields is rejected. No managed manifest is required. Ignore allowed_tools, eligibility, prefetch, predicates, workflows and resources as data; never transfer authority or follow resources. Dependencies come only from the recognized frontmatter metadata key.

Derive stable asset_id as `skill:` plus canonical SHA-256 of `{source_id,relative_package_path}`; identity is configured source/relative path, not display name or file hash. Output kind=skill, configured source_id, source_locator=resolved SKILL.md path, captured_at=this scan's UTC capture, source_version and identity.package_version=supplied version or null, identity.package_id=frontmatter name, content_hash=SHA-256 of original SKILL.md bytes, metadata as above, availability=unknown, stale=false for current valid captures. Retain normalized instruction body in the internal bounded searchable representation, excluding it from per-query catalog projection. Body is untrusted data, never gateway authority. This hash is not an immutable whole installed-package/resource revision or host-load guarantee.

Record the optional manifest's original digest in source provenance. A changed manifest version/language projection changes catalog/index revision even if SKILL.md hash is unchanged. Source generation content_hash is canonical SHA-256 over sorted staged entries `{relative_path,sha256}` for exact SKILL.md/optional-manifest captures; source_version=null without another defined source-level version input, never mtime-derived. Unchanged bytes/projection is a catalog no-op; observation capture time may update without fake content change.

A local scan is complete only after bounded enumeration and all candidate path/byte/encoding/metadata checks succeed. Disappearance during capture, missing/unreadable root, read error, rejected candidate or exhausted budget fails the whole scan, retains prior generation and records incomplete/stale/rejection evidence with no removals. A complete successful scan removes a prior package only after rechecking its configured-source-relative location and confirming directory or SKILL.md absent by ordinary nonexistent-path result, while source root remains present/readable. Permission error, symlink or invalid replacement is not absence. Persist each confirmed source-owned absence tombstone atomically with upserts. Omission in an incomplete listing never deletes; local absence evidence does not invent external inventory semantics. No execution, dependency installation, resource traversal, archive extraction, inference or host authority/currentness claim occurs in this reader.

Availability is scoped host evidence, separate from relevance and metadata revision. Discovery may include all statuses, with status/staleness visible. Runtime may offer only currently qualified available assets and revalidates before use. In 0.51 no qualified runtime snapshot adapter is enabled: imported/local records cannot assert host available, availability is unknown unless documented evidence supports needs_setup/unavailable, and runtime creates fail closed under section 7.6. Download success never establishes host usability.

## 5 State and persistence contract

| State | Allowed next behavior |
| --- | --- |
| accepted | Validate configuration and request, then route or fail. |
| routing | Select local, external, clarification, or an approved parallel workflow. |
| local_running | Propose or execute permitted tools, finish, ask, or escalate. |
| external_running | Continue with evidence and remaining permissions, then finish or ask. |
| parallel_running | Execute approved read-only branches, join, and transfer final ownership. |
| waiting_input | Suspend inference and tools; resume on explicit new input. |
| waiting_confirmation | Suspend the proposed mutation; resume only with a valid approval. |
| completed | Terminal success; immutable answer and trace. |
| failed | Terminal failure; retain partial evidence and an error code. |
| cancelled | Terminal cancellation; retain any actual side-effect outcomes. |

**RM17** Each transition MUST be atomic against a run state version. Resume and cancel operations MUST reject stale versions with HTTP 409. No transition from a terminal state may restart execution. A new attempt creates a new run linked to the previous one.

SQLite stores runs, events, tool_operations, approvals, idempotency_keys, and artifact_refs. Event sequence numbers increase within a run. Approval records retain a token hash, not the plaintext token. The default retention is seven days for traces and demo evidence, with explicit deletion available. Secrets are excluded. Local storage is not claimed to be encrypted by the application.

After a process restart, unfinished runs MUST become failed with interrupted. In-flight mutating operations are reconciled or marked unknown_outcome. The MVP MUST NOT automatically resume interrupted model loops or replay writes. Pending approvals expire on restart.

Restart recovery. The gateway runs recovery once at startup, before it accepts any run; it never runs while a run of this process is active. Recovery finds every run that is not in a terminal state, in accepted, routing, local_running, external_running, parallel_running, waiting_input, or waiting_confirmation, and ends each one in a single store transaction, so a run is recovered completely or not at all. In that transaction it first settles every tool operation of the run that is still pending (RM10). The MVP has no source to reconcile a write against, so a pending mutating operation is finished as unknown_outcome, and a pending read-only operation is finished as failed; both carry the error code tool_interrupted, and an operation whose tool is no longer registered is treated as mutating. Each settled operation gets a tool.finished event with the recorded ToolResult, replayed false, and recovered true. Recovery never runs a handler, never retries an operation, and never offers a settled operation again as work to do: a later proposal of the same call replays the recorded outcome (RM10), and an unknown_outcome blocks handoff (RM14). Next it expires every approval of the run that is still pending, by moving its expiry to the recovery time, so no token can be consumed (RM11). Last it moves the run to failed with error code interrupted and records run.failed with error_code interrupted, interrupted_state (the state the run was in), the operations it settled, model_calls rebuilt from the run's model.started events, external_calls, and the measured active_ms and waiting_ms (downtime is not counted, RM25). The failed transition releases the execution slot. A terminal run is never touched, and recovery of a store with nothing unfinished changes nothing, so running it twice is safe. A recovered run is never resumed: a resume of it is a terminal-state error, and a retry is a new run linked to the previous one (RM17). Recovery does not call any model.

A denied confirmation ends the run as cancelled with user_denied and performs no mutation. An expired waiting state ends as failed with input_expired or approval_expired. Waiting releases the active execution slot; a resume must reacquire it and may return 429 without consuming the approval.

Confirmation and resume. A resume in waiting_confirmation (section 7.4) carries approval_id, token, and approve. A body of another shape, such as input text, is 400 invalid_resume_input and the run keeps waiting; a stale version is 409. An approval older than five minutes, checked against the approval record, ends the run as failed with approval_expired, whether the resume approves or denies, and the wait counts toward waiting_ms of the run.failed event. An approval ID or token that does not match the pending approval is 403 with code approval_invalid; the run keeps waiting, nothing is consumed, and nothing is mutated. This check comes first, so a resume without the token neither expires the run nor sees a 429. The approval is consumed in the same store transaction as the resume or the cancel, so a resume or cancel that fails keeps it; this holds when two gateway processes share one store file: the resume takes the execution slot inside that transaction, so a second process that takes the slot after the first check makes the resume 429, the transaction rolls back, the approval stays pending, and the same approval works once the slot is free again (RM10, RM11, RM17). The gateway does not lock the store file against a second process. An approval whose run moved past its state version is void and no longer pending. A matching resume with approve=false consumes the approval and ends the run as cancelled with reason user_denied; its run.cancelled event carries the approval ID and the model-call and timing fields. A matching resume with approve=true first checks that the execution slot is free (429 otherwise, approval kept), consumes the approval, returns the run to the state that suspended it, and opens a new stage with the full per-stage limits of section 11, inside the entire-run limits, exactly as a resume after a clarification does. The gateway then executes the approved call once; its tool.started event carries the approval ID. The wait counts toward waiting_ms. A replay of a used token cannot execute again: the run has moved on, so the replay is 409 (stale version) or, for a terminal run, a terminal-state error, and the executor would replay the recorded outcome in any case (RM10). The gateway sweeps expired confirmations like expired clarifications.

Clarification and resume. A clarification suspends the run in waiting_input and records the question in clarification.required (section 8). The run's language is fixed by its first RouteDecision and is kept across every resume; the resume input never changes it, so an identifier-only reply does not re-detect the language. When a resumed run routes again, the gateway sets the new RouteDecision's language to the run's language before validation; a different language in the router's output is overridden there, not treated as invalid output (section 8). On resume the gateway appends the clarification question as an assistant turn and the resume input as a user turn to the conversation context, and records the input and the waiting time in a clarification.answered event (section 8). For RM05 identifier provenance only user turns and tool results count; the gateway's own question, which may list valid values, is not provenance. When the clarify decision carries a skill_id, the resumed run continues with that skill: the gateway checks the new input for the missing identifier without a routing generation and moves to local_running, or asks again if the input still lacks it. When the clarify decision carries skill_id null, no skill was chosen, so the resumed run routes again with a routing generation. Either way the resumed run records route.selected for the decision that continues it (section 8): a continuation records the gateway's decision made without a model call, a re-route records the new routing generation's decision. skill.loaded (RM06) is emitted when the run enters local_running; a clarify decision loads no skill body, so the clarification itself emits none. A resume opens a new local stage charged under section 11. A run asks for clarification at most the configured number of rounds (section 11); when a further clarification would be needed, the run ends as failed with error code missing_input.

OpenClaw sessions (spec 0.47, RM33). The host owns the session and sends the conversation on each request. Each client-owned chat request remains a separate run under section 7.2; the plugin introduces no gateway run state.

### 5.1 Recommendation persistence and lifecycle (spec 0.51; RM36, RM37)

Recommendations use dedicated scope-keyed SQLite objects/events/idempotency/feedback tables alongside the run store. They do not add execution states or change run recovery/retention. Creation atomically takes the separate nonqueued slot, claims idempotency, inserts computing at state_version 0 and event seq 1 accepted; overload leaves no orphan object or claim. Every actual lifecycle transition increments state_version once with its event and final idempotency response in the same transaction.

Closed transitions are computing→ready/failed/cancelled, and ready→chosen/cancelled/expired. Asset and none choices become chosen; cancel becomes cancelled. No_match/empty_catalog permit none/cancel, never asset. Ready expiry is ready_at plus the section 14.5 choice interval, checked before every fresh action/read and by retention sweep; record expiry once, never extend it on GET/replay. Chosen/cancelled/expired/failed are terminal and never reopen. Feedback/audit after terminal does not change lifecycle or lifecycle version. Choice creates no FeedbackRecord, increments no feedback_revision and changes no correction history/adaptation. Only explicit FeedbackRecord creation/deletion/reset uses feedback CAS; unrelated choice and feedback can commit without conflicting on the other revision.

Disconnect cancels an unfinished create. Once ready commits, a disconnect cannot rewrite it. Cancellation wins a simultaneous timeout; terminal commit fences late results and later fallback. Startup computing objects become failed with internal reason interrupted, without automatic retry; ready survives until expiry. GET exposes stored failure; replay of original create returns its original recorded status/error and cannot recompute. Accepted failures may expose recommendation_id for diagnostic lookup.

A choice binds stored task/scope, original offered IDs/hashes/versions, catalog/host revisions and expiry. Unrelated catalog changes do not invalidate unchanged eligible offered content. Changed content/schema/version, removal, policy revocation or host unavailability returns asset_changed and requires a fresh offer. Discovery choice may record an unchanged needs_setup/unknown/unavailable preference; its checks use discovery eligibility and do not invent runtime availability. A historical choice receipt never grants loading/execution; host revalidation and genuine mutation approval are separate requirements. 0.51 discovery choices are preference records only; blocked host-use integration cannot convert them into use authority.

All request-bearing recommendation/event/idempotency/feedback data has the section 14.5 retention. Recommendation retain_until is fixed at created_at plus retention; feedback ends at the earlier of its own retention or its parent's retain_until. Purge removes text, derived vectors/caches and replay copies together, without altering historical execution-run policy. Source archives have separate rights/provenance retention and cannot justify keeping erased request text.

Delete/reset immediately removes matching feedback payload, its derived text/vectors/caches, and copies in recommendation/audit events and stored replay responses, increments scoped feedback_revision once and leaves only content-free envelopes/tombstones. This is an explicit privacy-erasure exception to payload append-only storage: keep original seq/envelope identity and mark erasure, never present erased evidence as intact. Tombstones last only the remaining original idempotency retention, then purge; no renewal. They hold keyed digests of the lookup, key, object and request (HMAC-SHA-256 under an instance-local erasure key kept outside the recommendation store, with the same protected-storage rules as the action registrations in section 7.6), the stable caller and scope, the endpoint, and the deletion state and times. They hold no request text, asset names, deleted response data, or plain SHA-256 of erased content: an erased envelope replaces task_id with its keyed digest. A replay is matched by recomputing the keyed digest. Replay of an erased action is 409 invalid_state; it cannot restore data. Repeated DELETE under the same key replays its content-free receipt. Keys after retention are fresh operations, never a renewed side-effect approval. Reset removes scoped feedback/adaptation state, not every historical recommendation/choice; retained chosen/cancelled state stays terminal. If applicable request erasure removes choice-bearing content, only its content-free terminal envelope remains and replay cannot restore it. Reset retains no hidden trained state.

## 6 Model adapter contract

**RM18** Model identity and provider configuration MUST be independent of orchestration logic. Swapping between two already supported adapters requires configuration changes and restart, not routing-code changes. Adding a new protocol may require a new adapter.

Every adapter exposes capabilities, generate, cancel, and health. The orchestrator requests capabilities explicitly and rejects unsupported combinations.

Request headers are a separate surface from the JSON body:

| Request header | MVP behavior |
| --- | --- |
| Authorization | Required. Bearer application token (section 3). A missing or invalid token returns 401. |

Request validation (RM19, AC16). Every check below runs before any run is created, so a rejected request has no run and its error carries run_id null. The application token is checked first (401), then the body (400), then the Idempotency-Key header (400), then the execution mode header (400, then 403), then a stored key (409 or a replay, section 7.4), then the execution slot (429).

- The body is a JSON object. A body that is not JSON, not an object, or has a field of the wrong type or an out-of-range value is 400 invalid_request. The error message names the field.
- model is one of the aliases the gateway serves, which GET /v1/models lists. An alias that is not served is 400 invalid_request. The gateway serves relaymind-client-tools only when client-owned execution is configured (RM08, section 7.2), so it never lists an alias it cannot run.
- Every body field that is not in the table above is rejected with 400 unsupported_parameter, and the message names it, with these exceptions: a field set to null counts as omitted; user (a string) is accepted because it changes no behavior; and a field that the table does not list is also accepted when its value is the API default, so a client that sends presence_penalty 0, frequency_penalty 0, logprobs false, or store false is not refused. Message objects have the same rule: a field other than role, content, tool_calls (assistant), and tool_call_id (tool) is unsupported_parameter, and so is a content part that is not of type text. Content is a string or an array of text parts, which the gateway joins without a separator. The legacy functions and function_call fields are unsupported_parameter.
- Idempotency-Key is blank, longer than 255 characters, holds a character that is not printable ASCII, or is sent more than once: 400 invalid_request (section 7.4).
- n is an integer; any value other than 1 is unsupported_parameter. stream is a boolean. max_completion_tokens and max_tokens are positive integers no larger than the operator's limit (default 32,768, a configurable limit, not a claim about any model), and supplying both is invalid_request. temperature is a number from 0 to 2 and top_p is a number above 0 and at most 1; a value outside these ranges is invalid_request. response_format is omitted or {"type": "text"}; json_object and json_schema are unsupported_parameter.
- Sampling and budget values are applied to the final-response generation and to the external generations that produce the answer. An external generation that is offered tools may propose a tool call instead of the answer, so it is part of the tool loop: it takes temperature and top_p but keeps its own token budget, because the final-response budget would cut off the call. Routing, skill, and format-repair generations keep their controlled settings. The operator declares which of max_output_tokens, temperature, and top_p the configured adapters accept. A value for an option that is not accepted is unsupported_parameter, except that the API default (temperature 1, top_p 1) is accepted and not applied. The default is all three accepted.
- messages is a nonempty array. system and developer messages come first, before any other message. The first message after them is a user message, and the last message is a user message (managed alias) or a user or tool message (client-owned alias). An assistant message has text content, tool_calls, or both. In a tool_calls entry, id is a nonblank string that no earlier message used, type is function, and function.arguments is a string holding a JSON object. A tool message follows the assistant message whose tool_calls it answers, directly or after other tool messages for the same assistant message. Its tool_call_id names exactly one of those calls, once; every call of that assistant message is answered before any other message. A tool message with no matching call is invalid_request. user, system, and developer text must not be blank.
- With the relaymind alias (section 7.2), a nonempty tools array, any tool_choice, an assistant message with tool_calls, and a tool message are each 400 invalid_request. parallel_tool_calls true is unsupported_parameter with either alias; false and omission are accepted.
- With the client-owned alias, tools is an array of {"type": "function", "function": {name, description, parameters}} with unique names of 1 to 64 letters, digits, underscores, or hyphens. A tool of another type, or a function with strict true, is unsupported_parameter. tool_choice is auto, none, required, or {"type": "function", "function": {"name": ...}} naming a supplied function; any other value is invalid_request, and so is a tool_choice other than none without tools. Omitted tool_choice means auto.

The standard response uses one assistant choice with a stable request ID and virtual model alias. Streaming uses chat.completion.chunk content or tool-call deltas and the appropriate terminal finish_reason followed by [DONE]. Already emitted answer text is append-only. The schema foundation is Chat Completions; this table defines RelayMind's narrower supported surface. [S5]

Response shape. The request ID is chatcmpl- followed by the run ID, and the model field is the requested alias, never a provider model. The body is object chat.completion, with created, one choice with index 0, an assistant message, and finish_reason stop, or tool_calls for client-owned tool calls. The response omits usage, because no truthful unified count exists across the local and external tokenizers (section 7.3), and omits system_fingerprint. A clarification (section 5) is the assistant content with finish_reason stop, and so is the explanation of a pending confirmation, which names the tool and the run ID and says that the native API or the demo UI approves it. It never contains the approval token. The stream is chat.completion.chunk objects with the same ID and model: a first chunk with the assistant role and empty content, one content chunk for each answer.delta event of the run in order, a final chunk with empty delta and the finish_reason, and [DONE]. The run finishes before the first byte is sent, because managed tool planning is buffered (section 7.3), except under answer_stream live (RM32, spec 0.31), where the stream starts with the first verified statement of the answer generation; an error before that is a normal error response with its status. Both forms carry X-RelayMind-Run-ID, and an error response carries it too when the failure has a run. A run that ends cancelled during a chat request, or failed with an error code that section 11 reports as run state (missing_input, input_expired, approval_expired, interrupted, or predicate_unmet), is 409 run_terminal; the message names that error code, and the run is never reported as a 500.

Binding and token (section 3, RM19). The gateway accepts a bind address only when it is localhost or an IPv4 or IPv6 loopback literal (the rule of section 6); any other address is refused at startup, not downgraded. A bracketed IPv6 literal such as [::1] is bound without its brackets. The application token is generated by the gateway with a cryptographically secure random source at startup, has at least 32 characters, and is required on every endpoint of this section. No caller or configuration supplies it. An unexpected failure is a fixed 500 internal_error; the operator log names its type and the code location that raised it, never its text (RM12).

### 7.2 Managed and client owned tools

The relaymind alias selects managed execution. It uses the installed skills and tool handlers. Supplying a nonempty tools array, tool_choice, or client tool-result messages is rejected to prevent ambiguous ownership. Managed tool activity is visible through native events, not through client-executed tool_calls. The chat response contains the answer, clarification, or an explanation that confirmation is pending.

The relaymind-client-tools alias returns tool_calls to the caller. The caller executes them and includes matching tool messages in the next request. The hub MUST NOT execute those tools or certify that caller-reported results are trustworthy. Gateway-installed business tools are disabled for this alias. A caller may supply procedural instructions; managed skill execution is demonstrated through the managed alias. Local routing may fall back to external generation before output is committed, but external fallback is not permitted after partial client tool calls have been exposed. [S6]

The client-owned alias MUST honor tool_choice, preserve tool call IDs, and reject tool results without matching calls. No global tool-execution authorization guarantee is claimed for tools executed by third-party clients.

Client-owned run (RM08, RM19, AC10). Each request of the alias is its own run. The caller sends the whole conversation each time, so a response with tool_calls completes its run, and the next request, with the matching tool messages, starts another. The run has no routing generation, because the offered skill catalog is empty. It records route.selected with a decision the gateway made itself: route local with reason code simple_skill, or route external with reason code execution_mode in external_only, and skill_id null. The model sees the conversation as sent and only the functions the caller supplied, narrowed by tool_choice: none offers no function, a named function offers only that one, and auto and required offer all of them. The gateway installs no tool of its own. A generation is admissible when it is non-blank text, or when its first tool call names an offered function with arguments that are valid against that function's parameters schema (the same strict check as RM09). With none the generation must be text; with required or a named function it must be a tool call, and the named one. Text where a call is required, a call where none was allowed, an unknown name, or arguments that break the schema is invalid output: one format-repair generation is allowed inside the local limits, and then the stop is an escalation (RM04) with reason code invalid_output, also when the limits leave no room for the repair. The repair exchange grows the request, so it is measured again before the next generation (RM13). Every generation of this run may be the response, so max_completion_tokens, temperature, and top_p apply to each of them, local and external; there is no tool loop to exempt. A tool_calls response carries exactly one call, because parallel_tool_calls true is refused; further calls proposed by the same generation are not exposed, and the model proposes the next one after the result. The call ID is the one the model produced and is preserved in the response; the gateway replaces it only when it is blank, was used earlier in the conversation, or repeats within the response, so the IDs of the conversation stay unique. A tool message is passed to the model as data, unchanged (RM12). The trace records tool.proposed for the exposed call (the proposal ID is the call ID, arguments redacted) and never tool.started or tool.finished, because the gateway executes nothing; run.completed names the model that proposed the call. The response is buffered and complete before any byte is sent, so external fallback (RM04) can only happen while nothing has been exposed, and one response never mixes local and external output. This backend does not forward a live provider stream (section 7.3); a text answer is published as answer.delta events and replayed.

The X-RelayMind-Execution-Mode header applies to both aliases. With the managed alias it selects the route for skill execution. With the client-owned alias, external_only sends the request to the external model directly, and local_only keeps the request on the local model; the rule that external fallback is not permitted after partial client tool calls are exposed is unchanged. local_only returns needs_external with both aliases when the local model cannot produce the answer or, for the client-owned alias, the tool calls. parallel_demo is admissible only with the managed alias, because its fixed workflow runs gateway tools and managed skills (RM15, section 9), which the client-owned alias disables; parallel_demo with relaymind-client-tools is rejected with 400 and code invalid_execution_mode. This is a request validation failure, like a tools array with the managed alias, not an operator policy decision, so it is not a 403.

On this endpoint needs_external is an error before any answer content is sent, because RM04 raises it before output is committed. The response is HTTP 422 with an error object carrying code needs_external, a message, the reason code, and the run ID; partial results stay in the native trace of that run. 422 is used because the request was valid and authorized and no service was unavailable: the task cannot complete under the effective execution mode, and a retry with the same request would give the same result.

### 7.3 Streaming and early feedback

**RM20** The compatible stream MUST contain only answer content or client-owned tool-call deltas, with protocol framing. Internal progress and a generic acknowledgment MUST NOT be injected into it to improve reported latency. The demo's early model-selected status is delivered through the native event stream. A standard chat client without RelayMind event support may therefore wait until a valid answer or tool call is ready.

Once answer streaming begins, final-answer ownership is fixed. A subsequent provider error fails the stream; the gateway MUST NOT silently append another model's replacement answer. A later correction is a distinct message or run.

The stream is built in one of two ways. A buffered stream, which the managed alias uses unless answer_stream is live (RM32, spec 0.31), is the replay of a finished run: the run has already validated and published its answer, so the stream sends the role chunk, one content chunk for each answer.delta event in order, the finish chunk, and [DONE]. No provider is called while it is sent. A live stream is produced by a backend that forwards answer text while the provider is still generating it (the client-owned backend of section 7.2 buffers and validates its generation instead, so it does not produce one; from spec 0.31 the managed backend produces one under RM32). It sends the role chunk, then a content chunk for each non-empty piece in the order received, and the finish chunk and [DONE] only after the provider finished. The role chunk is held until the first non-empty piece arrives or the provider finishes, so nothing is sent before there is answer text. In both, an emitted content chunk is never revised, reordered, or retracted, and the joined content chunks are the answer. A managed request without stream selects effective buffered semantics before acceptance, including its correction loop (RM32); a generic live backend is collected before responding. A client that disconnects from a live stream makes the gateway close the provider stream, which requests cancellation (section 7.4); a disconnect is not a provider failure.

Mid-stream failure (RM20, section 11). When the provider fails after the first chunk was sent, the status line can no longer change. The gateway then (1) asks the backend to record the run as failed (run.failed, error_code external_failed; a run that already ended never restarts, RM17), (2) sends one data event whose body is {"error": {"code": "external_failed", "message": <fixed text>, "run_id": <run ID>}}, which standard SDKs raise as an error, and (3) closes the connection without a chunk that has a finish_reason and without [DONE]. The message is fixed and carries no provider text (RM12). The gateway does not send a replacement answer, and it does not retry on another model. A failure before the first chunk, or of a request without stream, is a normal error response with its status: the run is recorded as failed in the same way and the response is external_failed (503) with the run ID and the same fixed message (section 11).

In managed mode, tool-planning output is buffered and validated. After the skill's explicit completion predicate is met, or a validated finalize proposal is accepted, the orchestrator starts a final generation with tools disabled, under answer_pass final (RM31, spec 0.31; under draft the validated draft is published and the final generation runs only when a guard requires it). This final generation counts against the model-call budget. Its text can be streamed without risking a later tool call in the same generation. A skill whose evidence predicate is unmet cannot finalize merely because the model requests it.

**RM31** Answer pass (spec 0.31). The skill-stage draft that meets the completion predicate MUST be publishable as the answer without a second generation. The option performance.answer_pass (section 14.1) selects final, the default, the baseline of section 12, and the only behavior before this revision (the second generation with tools disabled), or draft. Under draft the gateway publishes the validated draft when it is in the run's language and holds no tool-call JSON; otherwise, and whenever the caller sent a non-default answer option (section 7.1), the final generation runs and is validated as before, so the recorded answer_options are always what shaped the published answer. run.accepted records the option and run.completed records answer_pass_applied, the pass that produced the answer (section 8). The corpus of section 12.2 reports both settings. The case for draft is finding F1 of the 2026-10-23 analysis in `docs/EVIDENCE.md`. The default stays final until the offline regrade and a corpus run in this configuration report (section 12.3); the spec then revises the default with their numbers.

**RM32** Gated answer streaming (spec 0.31). The managed alias MAY forward an answer while the provider generates it, under performance.answer_stream = live (section 14.1; buffered, the behavior before this revision and the benchmark baseline, is the default). Only an answer generation streams: a generation offered no tools, which under live the gateway makes once the skill's pending work is empty (every tool the skill needs has a recorded result, through proposals or prefetch), in the final pass, and in the synthesis call; under buffered the external loop keeps offering tools as before, so buffered behaves exactly as before this revision. A generation offered tools is buffered and validated as before, so preamble text and tool calls never reach the stream. The forwarded text is held back per statement: the gateway splits the text at statement ends and forwards a statement only after the completion predicate's per-statement checks pass (a preserved and unnegated status word, no forbidden pattern, identifiers from the evidence); the completeness checks run when the generation ends. A completeness failure after forwarding ends the stream with the mid-stream error event of this section, records run.failed with error code predicate_unmet, and sends no replacement text (RM20); a per-statement failure is never forwarded, so a client never sees a statement the gateway rejected (RM16). A per-statement failure before any statement was forwarded takes the correction loop inside the run's limits, because nothing reached the client; after a statement was forwarded it ends the stream as a completeness failure does. The same request without stream, or under buffered, takes the correction loop as before. Live and buffered runs are labeled in run.accepted and reported apart (section 12.2). The gate for live (section 12.3): task success on the corpus at parity with buffered, with the streamed failures (live runs that ended predicate_unmet where buffered would have taken a correction) reported; a forwarded-then-rejected count is zero by construction and is not the gate. The expected gain is bounded (findings F3 and F7 of the 2026-10-23 analysis in `docs/EVIDENCE.md`): the answer is a small part of an external run, and streaming leaves the fixed cost of each call untouched, so live is P1 and follows the correction-rate work of section 4.4. With early_headers false, the response waits for the first verified persisted content or a terminal outcome; with early_headers true, headers and keep-alive comments precede answer content. Neither headers nor comments commit answer ownership or count as first useful content (RM20). The native answer.delta events of a live answer are written as the statements are forwarded.

Early response headers (spec 0.31). Under performance.early_headers = true (section 14.1; false, the default, is the behavior before this revision and the latency baseline), a streamed chat request receives its status line and headers, including X-RelayMind-Run-ID and a new header X-RelayMind-Events-URL that names the run's native event stream, as soon as the run is accepted, and an SSE comment line as a keep-alive while the run works; no chunk with content is sent before the answer, so RM20 holds, and a client that wants progress opens the native stream the header names. A run that ends without an answer under early headers ends the stream with the mid-stream error event of this section carrying its error code and reason code, because the status line is gone; a request without stream is unchanged. With early headers on, the first transport event of section 12.1 is the header time, is labeled so, and is never reported as first useful content.

Usage is optional in the compatible response when a truthful unified count is unavailable. The native trace MUST retain usage per model and call, including cache counts when the provider returns them. Counts across different tokenizers MUST NOT be presented as if they belonged to one model.

### 7.3.1 Verified live publication (spec 0.41; RM12, RM20, RM32, AC19)

The following contract is normative.

**Eligibility and execution policy**

`answer_stream_effective` is a run execution policy chosen before acceptance:

| Entry | Configured buffered | Configured live |
| --- | --- | --- |
| Managed chat, `stream=true` | buffered | live |
| Managed chat, `stream=false` | buffered | buffered |
| Native managed run | buffered | live |
| Client-owned alias | buffered | buffered |

Live policy permits progressive publication only from a selected managed skill's genuine answer generation: its request offers **no tools**, and it is the final pass, a post-evidence answer generation, or the post-join synthesis. The provisional `external_checklist` branch has no tools but is **not** an answer and never publishes. Routing, planning, repairs that offer tools, tool-enabled draft text and their tool calls remain buffered. With no selected skill/predicate, retain the existing buffered generic external answer; RM32 says MAY stream and provides no semantic gate for this case. Effective live is permission for eligible generations, not a claim that every run emitted progressive content.

Keep RM31 unchanged: a tool-enabled validated draft can be published through the buffered draft path when its existing language, tool-JSON and caller-option guards pass. Do not stream that draft early or force a new final call just because live policy was requested. A no-tools stage under `answer_pass=final` that the existing loop treats as a finalize proposal remains a proposal until its actual final generation; avoid publishing it and then calling `_final` again.

Keep an immutable set of the stage's offered tool names before clearing schemas. Pending work is empty only when each such tool has the required recorded successful evidence; never infer it from “some tool ran,” model text or merely a recorded failure. Publish the choice that latest outcomes govern this live eligibility check, so a later failed/unknown outcome does not revive stale success. Missing/truncated evidence still follows each predicate's `_latest` rules: performance diagnostics explicitly accept a successful truncated observation, whereas complete-result predicates do not. A failed eligibility check leaves planning/correction available. Use this rule after ordinary proposed tool executions and confirmed resumes as well as prefetch. Buffered policy retains its existing tool offers and loop behavior exactly.

**Stateful gate and equivalence obligation**

Freeze the generation's evidence snapshot, predicate ID and raw text stream. Never run the whole-answer predicate independently on sentences or classify a failure by matching English failed-check strings.

Use the existing `_STATEMENT_END` language as the delimiter rule: `。！？；;` or newline always delimit; `. ! ?` delimit only with following whitespace or true EOF. Preserve every original character and newline, including delimiters; do not strip/rejoin or normalize Markdown/CRLF. Hold ASCII punctuation pending lookahead and treat unfinished final text as an EOF tail. Provider chunk boundaries have no semantic meaning.

Segmentation alone does not establish a safe publication boundary. Retain original surrounding context and any ambiguous suffix before declaring safety: regex token boundaries, Chinese glosses, resource-subject detection, label/number attribution and multiline checklist labels must resolve independently of chunking. Adjacent safe statements may be held together when necessary; correctness takes precedence over prompt publication. Retaining the complete raw accumulated answer and an unpublished offset is acceptable within the existing bounded generation; do not introduce an unrecorded output budget.

For each existing predicate P and frozen evidence R, define explicit cumulative safety S and final completeness C such that for **every** answer A:

`P(A, R) == (S(A, R) and C(A, R))`.

At EOF, also invoke the existing whole-answer predicate as the authoritative backstop. The equivalence must be demonstrated by differential tests on both languages, existing predicate fixtures/review regressions, and adversarial continuations, not asserted from a handful of passing sentences. A rejected stable statement is never persisted or forwarded. A missing value alone is a completeness failure, not a statement rejection. An absent/ineligible evidence snapshot fails before any publication.

| Predicate | Cumulative safety from existing semantics | Completeness at EOF |
| --- | --- | --- |
| health_status_preserved | Every status attributed to returned service under `_stated_statuses`, including negation/gloss/resource boundaries, equals returned status | At least one attributed status; exact checked_at substring |
| deployment_reported | Existing deployment-like-ID rejection; in no-deployment branch existing Chinese assigned-ID and revision checks | Service mention; when deployment exists exact returned ID and deployed_at; no extra absence assertion requirement |
| incident_counts_reported | No existing cause phrase; every attributed labeled number equals its returned field, retaining existing specificity/precedence | Service mention and at least one value for each window/count label |
| deletion_outcome_reported | No other matched demo database; no existing deletion-negation phrase | Successful deleted=true evidence; returned database mention and deletion verb |
| performance_evidence_separated | No invented factual verifier: current predicate has no observation-truth safety check | Successful evidence (partial allowed), filled observations and filled hypotheses/insufficient-evidence sections using existing label grammar |
| health_checklist_separated | Health safety only over the exact existing outside-checklist projection | First draft checklist label, plus health completeness on that projection |

Checklist scope is particularly easy to change accidentally: current code uses the **first** draft label, removes through the **first** subsequent non-list observation heading (or EOF), and includes all subsequent text. It does not repeatedly toggle scope for later checklist labels. A list item `- Observation:` does not resume health checking. `_DRAFT_CHECKLIST_LABEL` contains `\s*` and can span newlines; retain an undecided heading prefix until its classification is stable. `_filled_sections` counts content only until the next recognized section label, and labels inside prose do not start sections. Retain line-start context even when a previous statement was already emitted.

At true EOF resolve the tail, safety and final completeness **before publishing any remaining tail**. If no delta has committed, a failure still takes the existing correction/escalation route. If earlier deltas committed, failure terminates without publishing an unchecked/missing-completeness tail. Entirely empty/whitespace generation never creates an empty successful answer or claims ownership.

Redaction is a second equivalence obligation: joined published content must equal the existing full-answer `scrub(A)` for an accepted A. Today `_publish` scrubs the whole answer before splitting. A configured secret may span provider chunks **and statement delimiters**, and whole-token replacement needs right-boundary lookahead. Keep any possible secret-match suffix, longest-first semantics and original token context; merging/delaying statements, up to buffering the answer when necessary, is allowed. Predicate verification still uses raw text, as buffered currently does; persist and forward only the scrubbed verified projection. Do not independently scrub each statement, and never persist unredacted gate buffers for debugging.

**Commitment, ownership and terminal behavior**

Treat publication as a serialized run operation: check active state/version, cancellation/deadline and dispatch authority; validate/scrub the stable unit; successfully append its nonempty delta; then commit the in-memory owner tuple `(call_id, model_id, dispatch_role)` and notify the transport. No await or concurrent generation can intervene between the persistent append and owner update. If append fails, forward nothing and terminate through the internal-error path. Publication checks must also prevent a terminal run receiving a late delta. Whitespace-only pieces do not establish an answer by themselves; preserve them with adjacent real content when safe.

Every later published unit must have the same tuple. A second generation by the **same actor/model** is still a replacement and forbidden after commitment. `DispatchAuthority` currently remembers only local/external and allows repeated claims by the same actor; it also permits `hand_off_to_external` without checking answer ownership. Guard both escalation/dispatch and publication centrally, rather than relying on the transport to notice replacement. Do not call `_publish` again on already-published generation text when `_generate` returns.

| Stop | Before committed content | After committed content |
| --- | --- | --- |
| Predicate safety/completeness rejection | Existing local repair/final escalation or external correction, unchanged budgets | `run.failed error_code=predicate_unmet`; one matching fixed SSE error, no replacement/retry |
| Provider failure, malformed/no-tools native call, incomplete iterator | Existing provider/invalid-output route appropriate to stage | Terminal `external_failed`; fixed SSE error, no replacement |
| Placement miss | Section 14.2.4 local_slow handoff/needs_external | Section 14.2.4(5): failed external_failed, local_slow, placement.deadline; SSE deadline_exceeded |
| Entire-run/stage time stop | Existing budget mapping and permitted handoff; no dispatch without run budget | Terminal failure, never handoff; retain named exhausted budget and deadline response semantics |
| User/native/disconnect/shutdown cancellation | Existing cancelled/cancel_requested | Same cancellation, never predicate_unmet/provider failure; retain earlier deltas |

Cancellation wins an overlapping timeout as 14.2.4 requires, with terminal transitions remaining single-use/versioned. Check cancellation and elapsed deadlines before processing each candidate statement, before persistence and after iterator termination. Entire-run time wins its placement tie; otherwise applied placement timeout wins local-stage tie. A provider failure must not be relabeled predicate_unmet just because its unfinished prefix lacks complete fields. A success `Completed` marker is provisional until the iterator actually ends without failure: some adapters emit usage afterward, and a late exception still fails. A cancellation-resistant adapter's late text never resumes publication or opens another generation. Request best-effort provider cancellation once on an early rejected generation and finish/await cleanup before another dispatch.

Keep `_generate` as the sole generation/budget/timing boundary, including `_finish_model_call` from #129 and placement handling from #130. Predicate success is task success, separate from transport/timing sample success. If a statement rejection stops reading early, record an interrupted/failed model call truthfully; a naturally completed generation failing only completeness can still be a successful provider timing sample. Do not fabricate complete usage, tool calls, finish reasons or successful samples from partial output.

**Chat/native transport and exact additive schema choices**

The following additive section 8 fields are validated by both Python and JSON validators. Older events lacking the additions remain valid; additions are required for newly produced applicable events:

```text
run.accepted.payload.answer_stream_effective: "buffered" | "live"
  # answer_stream retains configured "buffered" | "live"
answer.delta.payload.call_id: nonblank string
  # existing text:string and model:nonblank string retained
```

No new event, run state or HTTP error code is needed. Cross-event invariants (runtime/store checks, not merely JSON Schema): call_id references this run's model.started, model/actor agree with that generation, tools_offered is empty for progressively published deltas, all live deltas have one call_id, and no delta follows a terminal event. Historical answer.delta without call_id means generation identity was not recorded, never invented by a reader. Effective live is the policy label; draft publication and other ineligible generations may still buffer under it. If an actual-applied metric is desired later, specify it separately rather than pretending answer_stream_effective promises progressive output occurred.

Predicate SSE payload is exactly:

`{"error":{"code":"predicate_unmet","message":"the answer did not meet the skill's completion criteria; no answer was completed","run_id":"<id>"}}`.

Use a dedicated stream-error representation/typed terminal result for this stream-only code; retain existing `ApiError` status rules for genuine HTTP errors. Deadline/provider/internal payloads retain their stable existing codes and fixed safe messages; include reason_code when the terminal outcome supplies one. The transport must not run a generic zero-argument `live.fail()` that overwrites an already recorded predicate/deadline/cancellation outcome.

Expose committed store deltas while the accepted run task is still running (one consumer/cursor with seq IDs, or a notification queue backed by persisted events). `ManagedChat.complete` and `early_stream` currently wait for the full task before replay and therefore cannot become live merely by returning a queue from `_publish`. Observe task termination **and drain previously persisted deltas** without duplicating any event; emit a successful finish/[DONE] only after the run actually completed and all deltas were delivered. Partial deltas followed by failed/cancelled state never produce a success marker. Cursor-before-start/notification-before-check discipline must avoid missing the first append. Bound the notification mechanism or use store cursors; never block native execution forever on a nonexistent chat consumer.

With early_headers=false, wait for the first persisted verified content or a terminal outcome before creating the SSE response; precommit failures remain ordinary HTTP responses after recoveries are exhausted. With early_headers=true, preserve immediate headers/comments and send a terminal SSE error if needed; headers do not remove precommit recovery rights. Send the role chunk once immediately before the first content chunk. Native events keep store seq/replay ordering.

The response owns the orchestrator task until the live iterator closes, even if an intermediate ChatResult becomes available earlier. Disconnect/response cleanup requests cancellation through the existing bounded path, asks providers to stop, and does not write provider-failure events. Native run ownership remains independent of event subscribers. Completed idempotent replays use stored scrubbed deltas and no generation; failed/cancelled duplicate handling stays as specified.

**Existing predicate limits: do not silently strengthen them**

The old predicates are syntactic evidence gates, not general truth checkers. These existing evaluations return True:

- No deployment: `payments-api checked.` with NO_DEPLOYMENT. Criteria ask to state absence but predicate only forbids matched invented IDs/revisions. Adding an absence requirement must revise spec/criteria/predicate together and be separately tested in buffered mode.
- Health: `Healthy: payments-api; payments-api is unavailable at <checked_at>.` with UNAVAILABLE. A status preceding the ID is outside current attribution grammar. Do not promise every conceivable contradictory health assertion is rejected.
- Performance: `Observations: payments-api is healthy because aliens fixed it.\nHypotheses: None.` with METRICS. This predicate verifies evidence/section presence, not factual truth, exact counts or cause attribution. Strengthening it is a separate semantic change.
- Deployment: the valid deployment report followed by `Owner account bogus-account-99.` still passes. It rejects its specific deployment-like ID patterns, not every identifier-shaped string.

Likewise exact timestamp/ID checks are substring tests, not semantic entailment. A claim that RM32 verifies every arbitrary statement against all tool facts would exceed the current predicate contract. Preserve this limitation explicitly; add no universal “every number/ID must appear in evidence” rule. Tool-enabled generations and native calls never leak through managed content; the existing `holds_tool_call_json` guard applies to RM31 drafts only. Extending that textual guard to every final/external answer changes acceptance semantics and needs its own spec-first decision, rather than an unannounced live-only strengthening.


### 7.4 Native run API

**RM21** The demo MUST use the following RelayMind-specific endpoints, backed by the same orchestration service as chat:

| Endpoint | Contract |
| --- | --- |
| POST /relay/v1/runs | Accept messages and execution_mode; return 202 with run_id, state_version, and events_url. Modes: auto, local_only, external_only, parallel_demo. |
| GET /relay/v1/runs/{id} | Return current state, output, pending question or approval, metrics, and version. |
| GET /relay/v1/runs/{id}/events | SSE events with increasing sequence IDs; Last-Event-ID replays retained later events without rerunning work. |
| POST /relay/v1/runs/{id}/resume | Accept expected_version and either input (the input text, recorded in clarification.answered, section 8) or approval_id plus token and approve boolean, matching the waiting state. Return 202. A body that does not match the waiting state, including a missing or blank input in waiting_input, or a missing or non-boolean field in waiting_confirmation, is rejected with 400 and code invalid_resume_input; the run keeps waiting and its version is unchanged (section 11). An approval_id or token that does not match the pending approval is 403 with code approval_invalid; the run keeps waiting (section 5). |
| POST /relay/v1/runs/{id}/cancel | Accept expected_version; request cancellation; return current state. |
| GET /healthz and GET /readyz | Process liveness and readiness of the configured execution mode; model warm state is explicit. |

A native run takes no model alias and always uses managed execution.

Native bodies and views (spec 0.17 and 0.18, RM21, AC11). Every native endpoint, /healthz, and /readyz require the application token (section 3, 401). The checks of POST /relay/v1/runs run in this order, all before a run exists: the token (401), the body (400), the Idempotency-Key header (400 invalid_request), the execution mode (400 invalid_execution_mode, then 403 execution_mode_forbidden under the same operator policy as the chat header), then a stored Idempotency-Key (a replay, or 409 idempotency_conflict), then the execution slot (429, nothing created). The body is a JSON object with messages (the managed-alias message rules of section 7.1: user, assistant, system, and developer text messages, the last one from the user) and an optional execution_mode (absent or null is auto). Any other field, including model, is 400 unsupported_parameter, named. The 202 response has run_id, state, state_version (the run version when it was accepted), and events_url (/relay/v1/runs/{run_id}/events). The work continues after the response: the run is not tied to the request that created it.

GET /relay/v1/runs/{id} returns run_id, state, state_version, requested_execution_mode and effective_execution_mode (from run.accepted), output (the joined answer.delta texts of a completed run, otherwise null), error_code and reason_code (a failed run's codes from run.failed, so needs_external, workflow_unavailable, and the run-state failures of section 11 are visible here, otherwise null), pending_question (while the run is in waiting_input: question, language, reason_code, skill_id, missing, and waiting_seconds from the latest clarification.required, otherwise null), pending_approval (while the run is in waiting_confirmation: approval_id, tool_name, proposal_id, arguments, target, state_version, expires_at from the latest confirmation.required, plus token, otherwise null), metrics, and events_url. metrics has active_ms and waiting_ms (the terminal event's values for a finished run, otherwise measured from the store's state intervals, RM25), model_calls, and external_calls (counted from model.started events by actor). The token is returned once: it is in the first read of the run that sees the pending approval and is null in every later read, so a caller that loses it can only cancel the run or let the approval expire. It is never written to the store or the trace (RM11). The same read serves a run started by the chat endpoint, because a chat reply cannot carry the token. Reading the run first ends any expired wait (section 5), so a run is never shown as waiting past its limit.

GET /relay/v1/runs/{id}/events is text/event-stream. Each stored event is one SSE message with id set to its seq, event set to its event_type, and data set to the TraceEvent JSON object (section 8). The stream first sends the retained events with a seq greater than the Last-Event-ID header (all of them when it is absent), in order, then sends each new event as the run records it, and ends after the run's terminal event. It stays open while the run waits, and sends an SSE comment line as a keep-alive when it is idle. Replay reads stored events only: it calls no model, runs no tool, and writes nothing, so reconnecting never repeats work. A Last-Event-ID that is not a non-negative integer is 400 invalid_request. A client that disconnects leaves the run untouched and can reconnect with the last ID it saw; only a compatible chat disconnect requests cancellation.

POST /relay/v1/runs/{id}/resume validates in this order: the run exists (404), the body has an integer expected_version (400 invalid_request), the run is not terminal (409 run_terminal), the version is current (409 stale_version), the body matches the waiting state (400 invalid_resume_input), and the approval matches (403 approval_invalid). A run that is not waiting is 409 invalid_state. A body that mixes input with approval fields is 400 invalid_resume_input. The 202 response has the shape of the creation response, and the continuation runs in the background. A resume of an expired wait is 202 with the run already in failed (input_expired or approval_expired); that is run state, not an error (section 11).

POST /relay/v1/runs/{id}/cancel takes expected_version and returns 200 with the run view of GET. A waiting run is cancelled at once, with reason cancel_requested in run.cancelled and the pending approval voided. A running run is asked to stop: the gateway cancels its work and, for a bounded time, waits for the run to reach cancelled before it answers, so the returned state can still be active if the work did not stop in time (best effort). A terminal run is 409 run_terminal and a stale version is 409. A run that is active under a request that owns it, such as a compatible chat request, is 409 invalid_state: closing that request is its cancellation. Cancelling during generation and during an in-flight write is specified below.

Cancellation during generation and writes (spec 0.19, RM10, RM14, RM17, AC12). A cancel of a running run stops dispatch first: after the request no tool starts and no model call starts. The adapter of a generation in flight, local or external, is asked to cancel that generation ID; this is best effort, the provider may not stop, and the run does not wait for it. A late result of a cancelled generation is dropped: it cannot propose a tool, run one, or publish an answer. A tool operation in flight when the cancel arrives is finished like one a restart interrupts (section 5): a mutating tool as unknown_outcome and a read-only tool as failed, both with error code tool_interrupted, and tool.finished records it before run.cancelled. The handler itself cannot be stopped and may still complete. Its late result never rewrites the recorded outcome and never causes another side effect, so the write is neither replayed nor treated as undone. An operation that finished before the cancel keeps its recorded outcome, whatever it was. The cancelled run is terminal and retains every recorded outcome in the store and the trace; nothing resumes it, and a retry is a new run (RM17) that needs its own confirmation for a mutating tool (RM11). A cancel cannot undo an action that was already committed.

GET /healthz returns 200 with status ok while the process serves requests. GET /readyz reports, for each execution mode the operator policy permits, whether its required models are ready, and for each configured model its availability and warm state (available, warm, and the adapter's detail). warm is false while a local model is still loading. A mode is ready when its models are available and warm: auto and local_only need the local model, external_only needs the external model, and parallel_demo needs the local model, an external model, and an enabled workflow, so a gateway whose operator names health-and-diagnostic-checklist in enabled_workflows (section 14.1) and has both models ready reports parallel_demo ready. The response is 200 only when every permitted mode is ready, and 503 otherwise, with the same body; the gateway never reports an unavailable or cold model as ready (section 12).

Execution mode is constrained by operator policy. local_only never calls externally and returns needs_external when the task cannot complete locally. external_only bypasses local inference while using the same managed tools, skill catalog, and permissions. In external_only no local routing generation runs: the gateway records a RouteDecision it produced itself, route=external, skill_id=null, reason_code=execution_mode, in the same way as the bypass decision for an oversized router input (section 4.1), and skills_offered in run.accepted lists the managed catalog the external model receives. How the external model selects among those skills is part of the handoff (RM13); every load still emits skill.loaded (RM06). parallel_demo fails explicitly with error code workflow_unavailable when its configured workflow is unavailable (section 4.4). The compatible chat endpoint accepts the same values through the X-RelayMind-Execution-Mode request header (section 7.1), so chat and native runs share one mode enumeration and one policy check, and a standard chat client can run the auto versus external_only comparison without the native API. Both endpoints record the requested and effective mode in the run.accepted payload (section 8).

Without a usable local model (spec 0.31, RM26). When the launch file has no local_model table, or the gateway classified the configured local model as unavailable, allowed_modes may name only auto and external_only (a request for local_only or parallel_demo is 403 execution_mode_forbidden), auto runs as managed external execution (RM26), and the client-owned alias runs on the external model as in external_only; when the local model is unsuitable, auto runs the same way, but local_only stays permitted and runs locally, because the operator asked for it, and the run records the class; parallel_demo remains forbidden while the class is unsuitable. GET /readyz reports auto ready when the external model is ready, and reports the local model with its class and cause (ready, unavailable, unsuitable, or absent), in a local_model object with model_id (null when absent), status, and reason; a mode the class does not permit is reported not ready (spec 0.37). A launch file without a local_model table whose allowed_modes names local_only or parallel_demo is a startup error (section 14.1); for a configured local model classified unavailable, those modes answer 403 while it stays unavailable. With a local model, /readyz also reports, next to the local model, whether the placement policy currently predicts local routing within its limit and which model auto would use (RM27); auto is ready when that model is ready, so a slow machine whose external model is down is not reported ready for auto.

Chat responses include X-RelayMind-Run-ID for trace correlation. Confirmations for managed writes require the native resume endpoint or demo UI. Ordinary clients can read the pending-confirmation message but cannot approve it solely by sending a free-form yes. Clarification can be resumed natively, or submitted as a new chat request with complete context.

Chat disconnect (spec 0.24, RM14, RM17, RM19, RM20, AC12). When the client of POST /v1/chat/completions disconnects before the response is sent, with stream true or false, and the request owns a managed or client-owned run that has not ended, the gateway requests cancellation of that run by the same path as the native cancel: dispatch stops, the adapter of a generation in flight is asked to cancel it (best effort), and a tool operation in flight is settled as for a native cancel (a write is recorded as unknown_outcome and never replayed, section 4.4). The run ends as cancelled with reason cancel_requested and releases the execution slot. The gateway waits for the run to stop only as long as for a native cancel. A chat request that the server itself cancels (for example at shutdown) takes the same path. A response that was already sent, a run that already ended, and a request answered from a stored Idempotency-Key change nothing. A disconnect from the native events stream never cancels a run.

All execution-creating POSTs accept an Idempotency-Key: POST /relay/v1/runs and POST /v1/chat/completions (spec 0.18, RM17, RM21, AC11). Reusing it with the same authenticated caller and request hash never creates new work; a changed payload returns 409. Native creation returns the existing run reference. Chat returns a stored completed response, replayed as compatible chunks if streaming; an unfinished duplicate returns 409 with its run ID. Keys remain valid for the seven-day run retention window. The key does not authorize repeating a completed side effect. Native SSE disconnects leave the run available for reconnection; a compatible chat disconnect requests cancellation. Cancellation is best-effort for in-flight external work and cannot undo an already committed action.

Idempotency keys (spec 0.18, RM17, RM21, AC11). The header is optional, and a request without it behaves as before. A key is 1 to 255 printable ASCII characters and is sent once; any other value is 400 invalid_request, checked after the body and before the execution mode. A key belongs to the authenticated caller. The prototype has one caller, the holder of the application token (section 3), so its keys do not change when the gateway restarts and generates a new token. The request hash is the SHA-256 of the canonical JSON (RM10) of the endpoint and the decoded body, with, for chat, the X-RelayMind-Execution-Mode header value; a different endpoint, body, or mode is a different payload, and a stream flag is part of the body. The same key on the other endpoint is therefore a changed payload.

A key is stored only when a run is created, in the same store transaction as the run and its run.accepted event. A request that is refused before a run exists (400, 401, 403, 429) stores nothing, so the client can send it again under the same key. A request whose key is already stored creates no run, makes no model call, and runs no tool. If the stored hash differs, the response is 409 idempotency_conflict with run_id null. If it matches:

- Native creation answers 202 with the shape of the creation response for the existing run: its run_id, its current state and state_version, and events_url. The response carries the header Idempotent-Replayed: true. It is the same whether the run is still active, waiting, or finished.
- Chat answers from the stored run. A completed run is answered with its stored response and the same X-RelayMind-Run-ID: the joined answer.delta texts as the assistant message (or, for the client-owned alias, the calls recorded by tool.proposed with owner client), and, when the request streams, the same chunk sequence as a live response (section 7.1), one content chunk for each stored answer.delta in order. The id is the stored run's, and created is the time the run ended, so every replay of one response equals the others. Client-owned tool-call arguments are replayed as stored; if the store holds redacted arguments (RM12), the replay is refused with 409 idempotency_conflict instead of returning arguments that differ from the original response. A duplicate of a run that has not ended (active, or waiting for input or confirmation) is 409 idempotency_conflict with run_id set to that run, and a duplicate of a run that ended failed or cancelled is 409 run_terminal with run_id set to that run; a retry after a failure uses a new key and is a new run linked to the previous one (RM17). Both responses carry X-RelayMind-Run-ID.

Keys leave with their run: the seven-day retention (section 5) and explicit deletion remove the key with the run, and after that the key is unknown and a request that carries it creates a new run. A reused key never authorizes a repeated side effect: a duplicate never reaches the orchestrator, and a completed operation is replayed from its record by the executor in any case (RM10). Resume and cancel do not read the header: expected_version already makes a retry of them safe (RM17).

### 7.5 OpenClaw provider integration (spec 0.47, M9)

**RM33** RelayMind MUST provide an installable OpenClaw provider plugin using the host's public plugin SDK and the authenticated loopback chat API of sections 7.1 to 7.3. The plugin MUST use relaymind-client-tools. OpenClaw owns conversation state, tool execution, and its tool permissions and approval policy; RelayMind owns bounded inference, proposal validation, fallback before output is committed, and its run trace. The plugin MUST NOT execute host tools, import them into the managed registry, approve actions, or claim that RelayMind certified caller-reported tool results. No fork of OpenClaw is required. [S12, S13]

The initial supported surface is text and one client-owned function call per response. The host sends the resulting tool message in a subsequent request, which creates a separate RelayMind run. The plugin preserves message roles, tool schemas, complete arguments, call IDs, and result references. It advertises only capabilities that the gateway and the qualified host version support. It MUST NOT advertise vision, audio, Responses, parallel tool calls, managed skill selection, or live token forwarding for this buffered backend. Unsupported behavior-changing input is rejected explicitly, never silently removed. The public chat contract remains section 7.1; a compatibility gap that needs a gateway contract change requires another specification revision before implementation.

Host compatibility switches. The host builds each request from its own defaults and from per-model compatibility switches that a catalog entry declares. At the pinned release, recorded on the wire by #135 (spec 0.49), the defaults for a loopback base URL send stream_options with include_usage on every streamed request and, for a model marked reasoning, reasoning_effort; section 7.1 rejects both. The developer role is off by default for a loopback URL, but a developer switch turned on places each runtime context message after the first user message as a developer message, which section 7.1 also rejects. The plugin MUST declare the switches that keep the host inside the section 7.1 subset: no stream_options, no strict flag, no reasoning_effort, no developer role, max_completion_tokens as the token field, text input only, and reasoning off. It MUST also keep three message switches off (spec 0.49): strict message keys, which strip tool_calls and tool_call_id from the messages and so break every tool round trip, and the tool result name and the assistant message after tool results, which add a field and a message that section 7.1 rejects. A declared switch is a host-side adaptation: it does not widen the gateway contract, and the gateway keeps rejecting what section 7.1 rejects. A host or operator setting that the gateway refuses, such as parallel_tool_calls true, stays refused with its named error; the plugin documents it and never changes the value silently. #135 records the switches and defaults of the pinned release with captured fixtures. A switch the pinned host does not offer is a recorded gap, not a reason to widen the gateway. The real host at the pinned release confirmed this on macOS for a model declared in a config-file provider (#135 host probe, spec 0.49): with no switches it sent stream_options to a loopback URL; with the switches it sent only section 7.1 fields, never a developer message, a tool message name, or an assistant message after tool results; and strict message keys stripped the tool linkage, which the gateway's validator rejects in the next turn. Switches on a model the plugin supplies (a catalog or dynamically resolved entry) were not tested: the probe's one plugin-supplied model declared none and sent stream_options, so the plugin (#136) MUST show on the wire that the host honors its declared switches before it claims compatibility. The host also rewrites the tool call IDs it replays: it removed the underscores from a call ID, the same way in the assistant tool call and in the tool message. The gateway's check that a tool message answers a call in the same request therefore still passes, but no part of the integration may match a later request to an earlier proposal by the exact ID string it issued; only underscore removal was observed.

The plugin registers the provider, its available client-owned model alias, and authentication through the public SDK. It connects only to a configured loopback base URL; the Python gateway remains a separately started process. The operator transfers the gateway-generated application token to the host's supported credential mechanism. The plugin does not change token generation, write a token to diagnostic output, or send it to an external endpoint or redirect. A gateway restart requires the fresh token; a stale token fails with 401 and an actionable reconnect instruction. Catalog discovery and diagnostics distinguish an unavailable gateway from an unavailable model and do not turn /readyz's aggregate status into a claim that every mode is unavailable.

An explicit plugin execution-mode setting maps to X-RelayMind-Execution-Mode: auto, local_only, or external_only. parallel_demo is rejected for this alias. Operator policy, local absence, and fallback keep their existing meaning. Client-owned execution has no managed selector, prefetch, or skill stage; it does not gain RM27's managed skill placement merely by passing through the plugin. The integration MUST state this limit, and any future client-owned placement change requires its own specification revision and tests. An external-only setup must work without a local model.

Request size and advertised limits. The plugin forwards the host's conversation and tool catalog unchanged: it never trims, summarizes, or drops a message or a tool to fit a model. The gateway's existing request measurement decides admission under sections 7.2 and 11: in auto a request too large for the local model goes to the external model before any output, under local_only the existing needs_external and context rules apply, and a request over the external budget ends as context_limit_exceeded. The catalog entry advertises a context window and an output limit only from the gateway's configured limits, says which mode they describe, and omits a limit the gateway does not report where the host allows an omission; it never advertises a window the effective mode cannot serve. The host enforces the advertised window itself (recorded by #135, spec 0.49): it estimates the input and refuses a request that does not fit before sending it, so the gateway never sees it. An advertised window is therefore the larger limit the effective mode can use, the external one in auto and external_only and the local one in local_only; a local window advertised in auto would refuse requests that the gateway would send to the external model. No gateway endpoint reports these limits at 0.47: GET /v1/models lists aliases only, and readiness reports none. The plugin therefore reads them from its own settings, which the operator copies from the gateway's configuration (external_model.context_limit in the launch file, and the local context of the pinned model manifest's launch settings), and omits a limit that is not set there; it never estimates one. An endpoint that reports the limits is a gateway contract change and needs another specification revision. The host's system prompt and tool catalog are large, so #135 reports the token size of the captured requests against the configured local input limit; that size, not the routing policy, bounds how much of the host's work can run locally. A UTF-8 byte count bounds the token count from above: a request under the limit by that bound fits, and one over it is undecided until a tokenizer count; the report never counts an undecided request as needs_external. A count of captures rewritten after capture, such as sanitized ones, is a lower bound on the host's request: it can show that a request is over a limit, never that it fits, so the deciding count uses requests as the host sent them. The host also decorates the user message (a timestamp before the prompt and a runtime line after it), so the user text the gateway receives is not the operator's raw prompt.

The plugin preserves cancellation through the host request's abort signal to the HTTP request, so the gateway can cancel its owned run under section 7.4. It propagates HTTP errors and streamed error events as failures, never successful empty answers. It neither replaces emitted text nor retries a partially exposed response through another model. Requests are single-attempt by default; any host-controlled retry must be bounded and use a stable Idempotency-Key for the same inference payload, a new key for the next conversation turn, and the section 7.4 replay rules. A request retry never authorizes repeating a host tool action. Tests distinguish cancellation before admission, during a buffered generation, and after completion. The plugin maps gateway error codes to the host's error classes truthfully: context_limit_exceeded is a context overflow, needs_external is a refusal under the effective mode and external_failed a failure of this provider, 429 overloaded is a temporary overload of this provider (another run or an idle probe holds the execution slot; the request was not queued), 504 deadline_exceeded is a timeout, and 401 is an authentication failure that carries the reconnect instruction. A retry after 429 or 504 follows the bounded retry rule above. The host class names the retry consequence (spec 0.49, #138). The pinned host retries the same model for its transient classes rate_limit, overloaded, server_error, timeout, and output_limit (up to 8 retries in about 90 seconds; the #138 Linux VPS check saw each retry rewrite the conversation, so each was a new Idempotency-Key and a new gateway run); its transient retry takes no other class. A refusal that follows from the gateway's configuration and the request is therefore never one of those classes, because a rewritten retry meets the same configuration: needs_external whose reason_code shows the refusal repeats (context_limit, a request over the local context; execution_mode, a route the effective mode fixes; invalid_output, local output for this request that the gateway refused, which a retry asks of the same local stage), execution_mode_forbidden (operator policy refuses the configured mode), idempotency_conflict, and run_terminal (the key is held, or names a run the gateway never runs again) are the host's request format class (format), the class the host itself gives an unlabeled 400 or 422, which it neither retries on the same model nor counts against the provider's credential health. internal_error, workflow_unavailable, external_failed, predicate_unmet, and needs_external with any other reason_code, or none, stay failures of this provider (server_error), which the pinned host retries on the same model, and the plugin's message never calls them a configuration refusal: needs_external with capability_missing also covers a local generation the runtime failed (a connection error or a restart), and no_local_model, local_budget, and local_slow depend on the local model's status, load, and time, so a later attempt may succeed; external_failed carries the reason the run left the local path, or the reason its external stage stopped, so its reason_code cannot tell an external output the gateway refused from a transient provider failure. The plugin picks a class for what the failure is and for this retry consequence, never to steer a failover. A host decision to fail over to another provider or model after such a failure is host policy outside RM20; the plugin neither triggers nor hides it, and section 12.5 records it as a host decision, never as a RelayMind answer.

Plugin diagnostics correlate each inference attempt with X-RelayMind-Run-ID when returned, or the run ID in the chat response, without placing trace events, secrets, or progress into answer text. One OpenClaw turn can contain several RelayMind run IDs. A run ID unavailable before cancellation is recorded as unavailable, never invented. The native trace remains authoritative for actual model calls and per-model usage. Missing usage is unknown, not zero or evidence that an external call was free.

The plugin package pins the OpenClaw release and SDK against which it is built and tested, declares its compatibility range, and includes installation, configuration, token refresh, diagnostics, disablement, and removal instructions. Qualification starts with v2026.10.7; a different baseline is recorded explicitly with its source revision and captured request/response fixtures. The contract tests run the actual pinned host transport against the real gateway with model doubles and sandbox host tools. A successful source review or plugin load is not a passing live integration test. AC24 closes only with the deterministic tests and the separately recorded live evidence of section 12.5.

M10 extension to section 7.5 (spec 0.51; RM39): the separate recommendation integration never changes `managedSkillSelection:false` on the inference provider. OpenClaw owns installation, loading, execution, permissions and approvals. A read-only model-origin recommend tool is permitted only if separately qualified and declared in `contracts.tools`; it cannot submit choices/feedback/reset/delete or train adaptation. No such tool is required or enabled by this revision.

### 7.6 Recommendation API and trusted actions (spec 0.51)

**RM36** The gateway MUST persist a separate recommendation object with validated ordered events, atomic lifecycle versions/idempotency, bounded deadlines, disconnect cancellation, restart interruption and the stable recommendation errors of section 11.1. No recommendation invents an execution run ID.

The existing current generated application bearer is required on every endpoint, using constant-time comparison and restart token handover (RM19). Scope is one active operator-configured `(user_id,workspace_id)` per instance: opaque local labels, not verified person identity. The server derives it; body actor/user/workspace/credential identity overrides are invalid_request. Historical objects remain scope-keyed; foreign scope reads appear absent. Separate configured instances serve other active workspaces. This does not assert production multi-tenancy.

**RM37** Choices, feedback, inspection, deletion and reset MUST require a separately registered direct-input credential bound to the active scope. Only local operator setup can register it; no HTTP self-enrollment/credential-administration endpoint exists. The ordinary bearer cannot promote itself to a trusted action channel. Model/source/tool assertions such as actor=user are never evidence of direct input. No model-callable action helper is registered.

Local registration is a closed operator-owned record: `schema_version:1`, stable `adapter_id`, `user_id`, `workspace_id`, `credential_sha256`, `enabled:boolean`, `host_identity`, `session_mapping`, `qualified_contract_revision`. The last three are nonempty bounded string references to the separately qualified adapter contract and its operator configuration, not arbitrary request-supplied authority. A production OpenClaw registration MUST NOT be enabled in 0.51: HOST-ACTION-AUTHORITY remains blocked. Deterministic trusted-adapter doubles may exercise the backend boundary and do not qualify a real host/person. No invented host session-mapping wire contract is implied by storing a qualification reference.

The action credential is at least the section 14.5 random-byte minimum, given once by local setup to protected host storage; only its SHA-256 digest and registration metadata are stored gateway-side. Send it only in `X-RelayMind-User-Action-Token`, alongside the current bearer; never in body/query/model context/tool arguments. Derive adapter/scope from the digest match to an enabled registration. Missing/invalid/revoked/wrong-scope credentials yield user_action_required, including replay. Rotation disables the old digest before enabling replacement, keeps stable adapter caller/idempotency identity, and registrations survive restart. Document resolved private paths: owner-only Unix access and user-restricted native Windows access. This trusts a qualified adapter's handling of direct input; it does not protect against arbitrary code in a compromised host.

1. the current bearer;
2. where required, action registration, authentication and scope;
3. bounded parsing;
4. for a runtime create in 0.51, 503 recommendation_unavailable, with no object, key claim or event;
5. the scoped idempotency lookup;
6. a privacy tombstone, a conflict, or a request in progress;
7. the original result, for a retry;
8. fresh expected-version, lifecycle and eligibility checks;
9. the mutation.

Timing storage and estimates (spec 0.38, RM17, RM25, RM27). The gateway records one sample for every actual generation, including failed and cancelled calls, across managed, client-owned, and fixed-workflow execution. Counts come from reported usage; an unreported count stays null, including input tokens on a failed or warm-up call. A selector's self-report is not an actual gateway call or a timing sample. Warm-up and probe samples have no user run and do not affect user budgets. Samples follow the store's run-retention duration (seven days by default); explicit run deletion removes linked samples. At most 1,000 samples per model and purpose remain, newest by recorded_at and then insertion order. Estimate queries ignore expired samples even before maintenance purges them.

Rejected optional measurements (spec 0.38.1, RM14, RM16, RM25, RM27). When an actual generation reports cached_tokens greater than its known input_tokens, the cached count is unavailable: the gateway records cached_tokens null in both model.finished usage and the timing sample (and in a warm-up result), retaining the valid input/output counts and actual monotonic timings. Null means unavailable, whether unreported or rejected, never a fabricated zero. The gateway emits exactly one warning for that observation through the standard logger with the fixed diagnostic `invalid_cached_tokens: cached_tokens exceeds input_tokens; recorded as unknown`. The warning contains no provider text, raw values, model/run identifiers or credentials. This normalization applies to managed, client-owned, fixed-workflow, warm-up and probe calls; it preserves execution success, failure, timeout and cancellation rather than allowing optional measurement validation to replace them. Strict stored/imported ModelTiming validation still rejects contradictory counts; seed files are not normalized. Other measurement constraints and database errors are not suppressed.

Estimates group samples by actual actor, model, and purpose, so local and external calls cannot mix even when model names match. They use successful samples only. Cached tokens above zero identify a warm prefix, zero identifies a cold prefix, and null identifies neither. Warm and cold effective prefill rates are separate medians of input_tokens / first_token_ms, in tokens per millisecond, using positive known terms. Effective decode rate is the median of output_tokens / (duration_ms - first_token_ms), again using positive known terms. These rates are prediction inputs, not claims of exact internal model throughput. Missing usable samples give an unavailable rate, never a fabricated constant. Expected output and external call duration are medians of the relevant successful observed counts and durations; zero reported output remains a measurement, while null is omitted from that median. A purpose's output cap is the expected-output fallback, not a fallback duration. Unknown prefix measurements may contribute duration/output medians but never silently become cold samples.

Skill outcomes are materialized once when a run becomes terminal, without scanning complete event histories when placement reads them. Local success counts a selected skill completed without external handoff after at least one non-routing local generation. Local escalation counts an actual handoff after such an attempt, even if external execution later fails or is cancelled, or an auto run that ends needs_external after that attempt. Routing-only runs, warm-up/probes, unplaced skills, pure cancellations, and local_only failures do not enter that completed-versus-escalated denominator. A parallel workflow run (section 4.4) is not a local placement (spec 0.38.1): its local branch generation is not a local attempt, and its planned synthesis join (handoff.started with a workflow) is not an escalation, so that run enters neither count, even when its local branch fails; its draft and synthesis still count as the skill's actual external generations when the run completes. Local outcomes group by configured local model and selected skill. Expected external generation counts group by the actual external model and selected skill, use completed runs with external calls, and do not mix different external models or unselected-skill catalog handoffs. Run deletion and retention remove the run's outcome contribution. The local success rate and median external generation count are unavailable when their respective sample sets are empty; expected-wait applies only with the required measurements and uses at least one expected external generation.

RouteDecision fields MUST also satisfy these cross-field rules:

- route=clarify requires a non-blank clarification. Every other route requires clarification=null.
- A non-null skill_id MUST name a skill in the catalog offered to the router for this run (skills_offered in the run.accepted payload).
- In managed execution, route=local requires a non-null skill_id. route=parallel requires a non-null skill_id whose registry manifest declares a parallel-workflow ID that operator configuration enables, and an effective execution mode that admits the workflow (section 4.4, RM15); in local_only and external_only route=parallel is invalid. route=external allows skill_id null; when set, it carries the selected skill into the handoff (RM13). route=clarify carries a skill_id only when the gateway found a required identifier of that skill absent (RM05); a clarification the model requests carries skill_id null, and its clarification.required names skill_selection as the missing input.
- In client-owned mode the offered catalog is empty, so skill_id MUST be null; route=parallel is invalid (section 7.2).
- reason_code follows the route: route=local carries simple_skill; route=clarify carries missing_input; route=parallel carries parallel_workflow; route=external carries the reason for leaving the local path: complex_skill, parallel_workflow, context_limit, execution_mode, capability_missing, or, from spec 0.31, no_local_model, local_slow, or selection_failed; a skill selected without a local model routes external with its skill_id and reason no_local_model (RM26), and a skill whose stage the placement policy hands off routes external with its skill_id and reason local_slow (RM27). local_budget, invalid_output, and tool_failure are escalation reasons recorded in the trace (RM04), not routing decisions.
- language: the first RouteDecision of a run fixes the run's language; every later decision of that run carries the run's language, which the gateway sets before validation (section 5), so the validator never sees a conflicting value.
- A decision the gateway produces itself, the oversized-input bypass (section 4.1), the external_only decision (section 7.4), and the external route of a selected parallel skill whose workflow is not admitted (section 4.4), follows the same rules.

A decision that breaks any rule is invalid output (reason code invalid_output): it never triggers a tool and is handled under RM03/RM04. The RouteDecision validator at the routing boundary owns these rules and checks every decision before route.selected is recorded; the skills_offered membership check reads the run.accepted payload, whose shape the run.accepted validator guarantees. The validator checks the decision it is given; the language rule holds because the gateway sets the language of every later decision (section 5), so a resumed routing generation cannot flip it.

Reason codes include simple_skill, complex_skill, missing_input, local_budget, invalid_output, tool_failure, context_limit, capability_missing, parallel_workflow, and execution_mode (a route fixed by the effective execution mode, section 7.4). Spec 0.31 adds local_slow (a local generation the placement policy predicted over its limit, or that missed its deadline, RM27), no_local_model (a gateway without a usable local model: absent, unavailable, or unsuitable, RM26), and selection_failed (a selector chain that chose nothing, RM28) to the reason_code enum of RouteDecision and HandoffEnvelope under the same schema_version, an additive change like the fields spec 0.26 added to run.accepted; a decision stored earlier never carries them. They are operational labels, not generated chains of thought.

answer.delta additionally carries call_id (nonblank string) for progressively generated output (spec 0.41, section 7.3.1). Historical and gateway-rendered output may omit it; readers never invent a generation identity.

## 10 Caching policy

**RM24** Skill parsing and template loading MAY be cached immediately by content hash. Routing-result caching MUST be disabled for the first model benchmark. If enabled later, it uses exact request and context matching, a five-minute TTL, and a maximum of 256 entries.

Skill parse cache (spec 0.26). The gateway keeps parsed skill files (the SKILL.md text and the manifest) and the decoded text of declared resources (the templates and examples a skill loads) in a cache keyed by the SHA-256 of the file's bytes. A file with the same bytes is not parsed or decoded again when the registry is loaded again (section 4.2); a file whose bytes changed has a new key and is parsed, so a stale parse cannot be returned. The cache holds only parse results of well-formed files: an invalid file is never cached and is refused on every load. Every package is still validated against the registered tools, predicates, and fixed parallel workflows on every load, so the cache changes cost, not what is accepted, and the skill content hash and version (RM07) are the same with and without it. The cache is on, in memory, and not configurable. Reloading a registry (SkillRegistry.reloaded) re-reads every package from its roots and gives a new registry; a run keeps the version snapshot it started with (RM07).

The routing cache key includes the effective messages, language, caller permissions, skill and tool hashes, model revision, routing prompt version, and policy version. Only local read-only route choices are eligible. No semantic cache, authorization cache, mutation route cache, or cross-user reuse is included. A cached route still performs current authorization and executes required fresh tools; it is not a cached answer.

Routing cache policy (spec 0.26). The cache is controlled by the operator setting cache.routing in the launcher file (section 14.1). It is off by default, and it is off in the benchmark configuration (section 12.2): a gateway, script, or test that does not name the setting runs without a cache, and the first model benchmark runs with it off. When it is off, no entry is read or written and no cache.hit is recorded.

- Key. The exact messages of the run as the router receives them (role, text, the tool_call_id of a tool message, and the tool calls of an assistant message with their call IDs, names, and arguments, in order), the run's language, the execution mode, the caller's permissions and the tool names the operator policy enables, the name, version, and content hash of every skill offered to the router and the schema hash of every tool those skills allow (so a changed skill, manifest, resource, or tool schema is a different key), the identity of the local model (its model_id, which names the pinned artifact revision, section 6), the routing prompt version (the digest of the routing prompt and the routing functions offered, so it changes whenever either changes, with no manual step), the selector chain in force (each selector's name and version, spec 0.31, RM28), and the cache policy version (a constant that changes whenever this section changes; spec 0.31 changes it). The caller is the one authenticated caller of the gateway (section 7.1), so no entry is shared across users. The key is hashed with the canonical form of RM10 and RM17.
- Eligible entries. An entry is stored only after a routing generation chose a skill, the gateway built a validated route=local decision from it, and every tool the skill allows is read-only (no mutating tool, RM11). Clarify, external, parallel, and gateway-made decisions (bypass, execution_mode, degraded_mode, client_owned, clarification_resume, selector_chain) are never stored, and neither is a skill another selector chose (RM28). What is stored is the skill choice, not the decision, the answer, or any tool result.
- Hit. A hit needs an unexpired entry under the same key (five minutes by the monotonic clock, section 12; at most 256 entries, the oldest stored entry is evicted for a new one). On a hit the gateway skips the routing generation and the tokenizer count of the router input, and builds the decision from the cached skill choice with the same gateway rules as a resume (section 5): identifier provenance (RM05) is checked again and the route comes from the current registry entry (RM04). A result that is not route=local is a miss and the entry is dropped. The run then continues exactly as an uncached run: the skill is loaded at the version run.accepted recorded (RM07), the tools are the intersection of skill allowlist, operator policy, and the current caller permissions (RM08), every call is validated (RM09), and every tool executes fresh (RM10); no tool result is cached. A cached route therefore cannot grant a permission or skip an authorization check, and a run whose current permissions allow none of the skill's tools ends as capability_missing like an uncached run. A run counts the hit like any local run: zero external calls (RM01) and no routing model call in model_calls.
- Invalidation (AC13, RM07). Before each lookup and each store the cache drops every entry whose recorded skill hashes differ from the registry the run uses (a skill changed, was added to the offered set, or was removed) or whose recorded permissions or enabled tools differ from the current ones. A changed skill or permission therefore ends the dependent entries at once, not at the TTL, and the next request routes with a model generation under the new key. Before each lookup and each store it also removes every entry older than the TTL, counted as expired, so eviction counts only entries removed for space. The cache also exposes counters (hits, misses, stores, expired, invalidated, evicted) so an experiment can report them; a hit the gateway cannot use (not route=local) is counted as a miss.
- Labels. run.accepted carries routing_cache true when the cache is enabled for the run (section 8). Every route.selected of a run with the cache enabled carries routing_cache hit or miss (a hit has mechanism routing_cache, section 8); a gateway-made route.selected (bypass, execution_mode, degraded_mode, clarification_resume, client_owned, selector_chain) is a miss, because no cached choice was used. The demo UI shows the route mechanism, so a cached route is visible as one. A route.selected with mechanism routing_cache is made by the gateway, so it is not a model action for the first-model-action metric (section 12.1).

Prompt prefix reuse (spec 0.31, RM27). The routing request's first several hundred local tokens (the routing prompt and the skill functions) are the same for every request of a gateway, and the skill stage's instructions are the same for every request of a skill. The gateway requests cache_prompt explicitly, records the cached prompt tokens of every call (section 6), and lays prompts out so that the constant part comes first. In the external request the rules, the skill instructions, and the fixed completion criteria come first, and the run-specific values (the run ID, the remaining budgets) last. The skill stage keeps the skill description and the tool to call first and the skill body after the request (spec 0.35): putting the body before the conversation was measured on the pinned model on 2026-10-23 and lowered local completion and tool correctness (`docs/EVIDENCE.md`), so the layout changes only on a new measurement. Whether the runtime or the provider reuses the prefix is measured, never assumed: the latency experiment reports cached tokens per call (section 12.2), and a count the adapter did not read is reported as not measured. The pinned launch settings do not change for this; a slot pin or a slot count change would be a manifest revision under RM18.

Prefix or KV caching is controlled by the inference runtime or provider and is recorded separately. Reusing a prompt string in SQLite does not imply reuse of inference computation. Cache-on results MUST be labeled and reported separately from the uncached baseline: an exported statistics file (RM25, section 12.1) names the routing cache setting of the run that produced it (routing_cache on or off, off when the exporter was not told), and cache-on figures are never merged with, or presented as, the baseline. A cache-on measurement is an experiment of its own; the hypothesis and gates of section 12.3 are stated for the cache-off configuration. [S8]

M10 invalidation (spec 0.51; RM24, RM34, RM37–RM43): catalog/index caches key exact source/content/schema/catalog and representation/model/config revisions. Feedback/adaptation caches also key active scope and feedback_revision. Changed/deleted content and policy invalidate eligibility immediately; expiry/delete/reset remove derived private effects and stored replay copies under section 5.1. Failed rebuild keeps the last compatible generation and filters old versions. These caches never cache tool results or change the managed routing-cache policy above.

## 11 Budgets and failure behavior

Initial engineering defaults are listed below. They are configurable limits, not predicted timings; from spec 0.31 the launch file sets them in its budgets table (section 14.1), and every run records the values in force (RM03).

| Budget | Default |
| --- | --- |
| Routing input for fast experiment | At most 2,048 local tokens |
| Routing output | At most 128 tokens |
| Local execution | Four seconds active time; routing plus three further generations; at most two tool executions |
| Entire run | 60 seconds active time; at most eight model generations including routing and repair; at most six executed business tools |
| Tool timeout | Two seconds unless a tool declares a shorter timeout |
| External generation | At most 30 seconds per generation and six generations (external_seconds, external_generations), also bounded by the remaining run budget |
| Simultaneous requests | One active run in the baseline; reject additional work with 429 rather than hide queue time |
| Waiting state | Five minutes per wait, recorded as waiting_seconds and excluded from active execution time |
| Clarification rounds | Two per run; a third needed clarification ends the run as failed with missing_input |
| Selection time limit | Two seconds per selector that is not a model (RM28); a model-based selector is bounded by its generation's limits |
| Admitted calls per generation | Up to the per-stage tool limit of read-only calls in a local stage, the remaining entire-run tool limit in the external stage; a mutating call alone; a set whose new executions the remaining tool budget has no room for is rejected whole before anything runs (section 4.3, spec 0.34) |
| Local generation deadline | The placement prediction times placement.margin (default 2), capped by the remaining stage budget (RM27) |

The Local execution row is a per-stage limit. A run's first local stage starts at routing; a resume after a clarification opens a new local stage with the full per-stage limits, so a resumed run that routes again has its routing generation (section 5). The Entire run row bounds the sum of all stages, and waiting time counts toward none of them. The two model branches in parallel_demo are allowed within a single active run (section 4.4): the local branch uses the local per-stage limits, the checklist draft and the synthesis call each count as an external generation and in the entire-run generation limit, and the draft is bounded by external_seconds. The local-first per-stage limits do not constrain external-only baseline routing, but the total run limits apply to every mode. A skill that requires more local work is escalated instead of quietly increasing budgets.

Error contract. Every error response has the JSON body {"error": {...}}, where the error object has a stable code, a message, run_id (the run reference, or null when no run exists), and reason_code only when the failure has an RM04 reason code. The code is the contract; the message is for people. The statuses and codes are:

| Status | Codes | Cause |
| --- | --- | --- |
| 400 | invalid_request, unsupported_parameter, invalid_execution_mode, invalid_resume_input, context_limit_exceeded | A validation failure, including a resume whose body does not match the waiting state (section 7.4) and evidence over the external context limit (RM13) |
| 401 | unauthenticated | A missing or invalid application token |
| 403 | execution_mode_forbidden, approval_invalid | Denied access, including an approval ID or token that does not match (section 5) |
| 404 | run_not_found | A run that does not exist |
| 409 | stale_version, run_terminal, invalid_state, idempotency_conflict | A stale state version (RM17), a resume of a terminal run or a chat duplicate of a failed or cancelled one, a resume in a state that cannot take it, a reused idempotency key with a changed payload, or an unfinished chat request under it (section 7.4) |
| 422 | needs_external | A task that cannot complete under the effective execution mode (section 7.2) |
| 429 | overloaded | Another run holds the execution slot; the request is rejected, not queued |
| 500 | internal_error | An unexpected failure |
| 503 | workflow_unavailable, external_failed | An unavailable required model, or in parallel_demo an unavailable workflow (section 4.4) |
| 504 | deadline_exceeded | An exhausted time limit before streaming starts |

A failed run maps to this table by its error code: needs_external is 422, context_limit_exceeded is 400, workflow_unavailable is 503, internal_error is 500, and external_failed is 503, except that an external_failed run stopped by an exhausted time limit (the entire-run active time, or external_seconds) is 504 with code deadline_exceeded; its run.failed event keeps error_code external_failed and names the limit. predicate_unmet (spec 0.31, RM32) occurs only after a live stream forwarded statements: the stream ends with the mid-stream error event of section 7.3 carrying that code, the native API reports it as run state, and a request without stream never sees it, because a buffered answer takes the correction loop instead. A run that ended as missing_input, input_expired, approval_expired, or interrupted, or as cancelled, is not an error response to the request that created it: the native API reports it as run state with its error code (section 7.4). Internal errors carry a fixed message and omit credentials, exception text, and secret values (RM12).

After streaming starts, an unrecoverable failure is signaled as an error and connection termination, and recorded as run.failed. It MUST NOT produce a successful finish marker. The compatible client behavior for this failure is part of integration tests because SDK handling may vary.

An unavailable local model, meaning a missing local capability or a failed local generation, may route directly to external only when the operator policy permits degraded mode and external dispatch is permitted (an effective mode other than local_only, a configured external model, and room in the entire-run limits). Degraded mode is off by default. When it is on, the run hands off with reason code capability_missing, with the evidence it has so far; when the failure came before any routing decision, the gateway records its own decision first, route=external, skill_id=null, reason_code=capability_missing, in route.selected with mechanism degraded_mode. The handoff.started payload then carries degraded_mode true and local_failure (the cause), so the trace records degraded mode. Without the policy, or when dispatch is not permitted, the run ends as needs_external with reason code capability_missing. An unavailable external model does not make a complex request locally solvable. If external use is disabled, return needs_external with partial results. Read-only retries are limited to one for a transient failure within all budgets; model repair also counts toward generation limits. A gateway with no configured local model is not in degraded mode: it runs managed external execution with reason code no_local_model (RM26), and a selector chain that chose nothing hands off with reason code selection_failed (RM28).

An external stage that cannot finish ends the run as failed with error code external_failed. Causes are an adapter error, an unreachable endpoint, an answer that does not meet the completion predicate within external_generations, and an exhausted entire-run limit. The partial evidence stays in the trace, no local answer replaces the external one, and no result is invented (AC07). The run.failed event carries an RM04 reason code: the reason the external stage stopped when it stopped on one, otherwise the reason for the escalation. Evidence over the external context budget is a separate code, context_limit_exceeded (RM13). The HTTP mapping of both codes is in the error contract above.

### 11.1 Recommendation budgets and errors (spec 0.51)

Recommendation budgets/slots/job limits in section 14.5 are separate from all execution-run limits above. Never silently increase either. A custom effective budget is recorded and cannot claim standard acceptance unless its frozen protocol matches. There is no automatic retry of interrupted recommendation computation. Service elapsed starts at receipt of the authenticated create and includes body parsing/transport preparation through committed response serialization; the primary cap starts at its dispatch within that remaining clock. Validation before acceptance consumes that same total, not a fresh budget. Relative dispatch deadlines avoid cross-process wall-clock comparison.

Recommendation errors use the section 11 error contract with run_id null and an added recommendation_id (UUID or null): `{error:{code,message,run_id:null,recommendation_id}}`. Existing run and chat error bodies, codes and statuses are unchanged. Shared codes, including unauthenticated (401) and internal_error (500), keep their section 11 status. Messages are fixed safe text, never raw exception or credential text. This table lists the recommendation-only codes and the recommendation causes of shared ones:

| HTTP | Code | Meaning |
| --- | --- | --- |
| 400 | invalid_request | Malformed/unknown/oversized field, invalid enum/number/key/target. |
| 403 | user_action_required | Missing/invalid/revoked/wrong-scope direct-action registration, including replay. |
| 404 | recommendation_not_found | Absent or foreign-scope recommendation. |
| 404 | feedback_not_found | Absent/foreign-scope/purged feedback. |
| 409 | stale_version | Expected lifecycle/feedback revision differs. |
| 409 | idempotency_conflict | Scoped key or event ID reused with changed canonical payload. |
| 409 | recommendation_in_progress | Identical accepted operation is still in flight; no extra compute/wait. |
| 409 | recommendation_expired | Fresh ready choice after expiry; committed choice replay remains historical. |
| 409 | asset_changed | Offered content/schema/version or current eligibility changed; fresh offer required. |
| 409 | invalid_state | Fresh incompatible terminal action, or replay payload erased by privacy policy. |
| 429 | overloaded | Separate nonqueued recommendation slot is busy. |
| 503 | recommendation_unavailable | Disabled/no usable catalog/lexical generation, unsupported runtime binding, or interrupted create replay; stored reason distinguishes causes. |
| 504 | deadline_exceeded | Total budget exhausted before ready commit. |

Authentication/parsing/replay precedence is section 7.6. Expiry transitions once before fresh choice checks; stale expected versions are checked before fresh lifecycle/eligibility errors. Cancellation wins simultaneous timeout and prevents later attempts. A terminal create failure replays its recorded error; interrupted recovery uses recommendation_unavailable with internal reason interrupted, not another inference attempt.

### 12.1 Metrics

**RM25** Timings MUST use a monotonic clock for elapsed durations and UTC for event timestamps. Record both server arrival and UI submission; never subtract timestamps from unsynchronized hosts.

| Metric | Definition |
| --- | --- |
| First transport event | First received byte or status event; reported as transport latency only. |
| First model action | First validated model-produced route, clarification, or tool proposal available to the client. |
| First useful content | First displayed result supported by task evidence, or the first necessary clarification question. Generic acknowledgments do not qualify. |
| First answer token | First nonempty answer-content delta in the compatible stream. |
| Completion latency | Request to successful final answer; active time and human waiting time reported separately. A wait that ends the run (input_expired, approval_expired, user_denied) counts toward the waiting_ms of its terminal event. |
| Local completion rate | Simple-task cases successfully completed with zero external inference calls, divided by all simple-task cases. |
| Tool correctness | Correct tool and semantically correct arguments against fixture expectations; schema validity reported separately. |
| Escalation quality | Missed necessary escalations and unnecessary escalations, reported separately by class and language. |
| External usage | Actual requests and per-model input and output tokens, including abandoned parallel calls. An abandoned branch call is in model_calls and in external_calls of the terminal event. |
| Parallel extra call | The duration of the synthesis call or calls of the parallel workflow, from the monotonic clock, reported as extra_call_ms in the workflow object of the terminal event (section 8), next to the elapsed time of each branch. |
| Generations per completed run | Spec 0.31: the model calls of a completed run, by actor and purpose; the measure of RM29, RM31, and the admitted-calls rule of section 4.3. |
| Wasted local time | Spec 0.31: the local active milliseconds of a run that ended with an external answer or as needs_external, reported as a distribution per configuration (RM27). |
| Prediction error | Spec 0.31: predicted_ms minus the actual duration of each local generation, as a distribution; a prediction is never reported as a measurement (RM27). |
| First token per call | Spec 0.31: first_token_ms of every model call, by model and purpose, from the monotonic clock (section 6); the fixed cost of an external call is reported from it, never inferred from total durations. |
| Selection accuracy | Spec 0.31: the share of corpus cases for which a selector chose the expected skill, per selector, language, and class, against the sidecar file of section 12.2 (RM28); and, on the selection benchmarks of section 12.4, precision, recall, and Jaccard per selector as the main metrics, with the none-rate and selection latency. On the corpus the expected set has one skill, or none for a case that expects a clarification first. |
| Corrections per completed run | Spec 0.31: external answer generations the completion predicate rejected, per completed run, with their summed duration; the measure of the correction cost (section 4.4). See finding F6 of the 2026-10-23 analysis in `docs/EVIDENCE.md`. |
| Streamed failures | Spec 0.41: export configured answer_stream and answer_stream_effective per case, terminal error_code and task success; summarize each effective policy separately and retain every failure. The paired live/buffered corpus comparison uses one final revision and frozen timing prior, and is required before changing defaults. Spec 0.31: live runs that ended predicate_unmet; reported with task success next to buffered, which is the gate of RM32. The 500 ms hypothesis is p95 first model action at or below 500 ms for the warmed, short-context, concurrency-one experiment with routing-result caching disabled. The UI displays this as model action latency, never as completed-answer latency. Report whether it is met on each tested machine; do not average a slow Windows result into a fast Mac result. A missed target is a finding, not grounds to fabricate an early response.

### 12.2 Reproducible experiment

The correctness corpus contains 40 English scenarios: 12 simple, 10 complex, 6 ambiguous, 6 requiring mutation confirmation, and 6 adversarial or fault scenarios. Simplified Chinese versions of the scenarios are optional and best-effort; when present, results are reported per language and never merged into the English results. Each case includes fixture state, acceptable tools and arguments, required evidence, expected permissions, and a grading rubric. Freeze the corpus before comparing candidates and keep development examples separate.

Run auto, external_only, and local_only against the same fixture snapshots. Baselines use the same skills, tool descriptions, execution rules, and output criteria. Select identical relevant external data where the route permits it. Count provider calls; do not infer cost savings from latency. Monetary estimates require actual provider rates and a dated rate source and are optional.

For the latency experiment, use 12 short English prompts, including routing, clarification, and simple tool tasks. Perform three warm-up requests per model configuration, then ten measured runs per prompt in randomized order. Record errors and timeouts rather than dropping them. Chinese prompts may be added on a best-effort basis and are reported per language. Report p50, p95, sample count, and timeout fraction. Report cold startup separately, including model load time. Exact-route caching stays off (cache.routing false, section 14.1) and the exported statistics say so; runtime prefix-cache behavior is explicitly recorded.

Record OS version, CPU, GPU, RAM, backend, thread settings, model hashes, quantization, context settings, sampling parameters, runtime and application revisions, external endpoint region if known, and test time. Shared provider load remains a potential source of variability. Actual hardware is filled into the benchmark report after execution; no reference machine performance is assumed here.

Correctness corpus (spec 0.28, #32). The corpus is one versioned file, `evaluation/corpus.v1.json`, with the sandbox seeds it names. Each case has an ID, a class (simple, complex, ambiguous, mutation, or adversarial), a language (en, or zh for a best-effort Simplified Chinese version of an English case, marked best_effort and linked to its English case), the prompt, the fixture seed (a sandbox seed file under `tests/fixtures/sandbox/`, section 9), the expected permissions (the caller permissions the case runs with, section 14.1), the expected route in auto mode (local, external, or clarify), the acceptable tool calls (groups of calls of which at least one must be proposed, and further calls that may be proposed; an argument is an exact value, a list of acceptable values, or any value), the clarification answer and confirmation decision the runner gives, the expected run outcomes, the required and forbidden evidence (patterns that the final answer must and must not contain), the expected sandbox databases after the run where the case can change them, and a grading rubric in words. The prompts must not repeat a development example: the skill examples (`skills/*/examples.json`) and the prompts of the live acceptance harness are development examples and are never corpus cases. The corpus is frozen by a SHA-256 digest of the canonical JSON (RM07) of the corpus and every seed it names, kept in `evaluation/corpus.v1.lock.json`. The runner refuses a corpus or seed whose digest differs from the lock, and the export records the digest. A change to a frozen case is a new corpus version, recorded in the changelog; results of two versions are never merged.

Corpus runner (spec 0.28, #32). `scripts/run_corpus.py` starts llama-server from the manifest and, for each case and each of auto, external_only, and local_only, a new gateway with `relaymind serve --config` (section 14.1): a new store, a new sandbox working copy from the case's seed, the case's permissions, the checked-in skills, the routing cache off, and the configured external endpoint. So every mode of a case starts from the same fixture snapshot. The runner creates one native run (section 7.4) with the case prompt and the mode. When the run waits for input it resumes with the case's clarification answer (it cancels the run when the case has none); when the run waits for confirmation it approves only when the case says approve and the pending call is an acceptable call, and denies otherwise. It reads the trace back from the store. The grades are computed from the trace, the terminal state, and the sandbox state after the run:

- Task success: the outcome is one of the expected outcomes, a completed answer contains every required evidence group, no answer contains forbidden evidence, the tool calls are correct, every started tool needs only the case's permissions, no mandatory confirmation was missed, the sandbox ends as expected, and an expected clarification was asked.
- Local completion: a simple case with task success and zero external inference calls (external_calls of the terminal event is 0). The rate divides by all simple cases of the language and mode.
- Tool correctness: every model-made tool proposal of the run matches an acceptable call, and each required group is matched by at least one proposal. With prefetch on, a gateway-made proposal that was admitted also counts toward a required group, because the evidence the case needs was gathered; it is never judged against the acceptable calls (prefetch correctness is a separate measure) and it is reported apart as gateway_proposals. A run without a proposal of either kind is correct only when no group is required. Schema validity is reported separately: the proposals not rejected with unknown_tool or invalid_arguments, over all proposals.
- Escalation: a run escalated when it made an external inference call. In auto mode, a case whose expected route is external and did not escalate is a missed necessary escalation, and a case whose expected route is local or clarify and escalated is an unnecessary escalation; both are reported separately by class and language. external_only and local_only do not choose a route, so they have no escalation grades.
- Missed mandatory confirmation: a mutating tool that started without a confirmation.required event for its proposal earlier in the trace (RM11). The count is reported for every mode, together with the mutation cases where the model reached a confirmation.
- Provider calls: local and external inference calls and input and output tokens per model, from model_calls and external_calls of the terminal event.

The report gives exact numerators and denominators per mode, class, and language; Chinese results are reported apart and never merged into the English ones. A run that does not come to rest within the runner's time limit is cancelled and graded as a timeout, never dropped. In local_only a case whose expected route is external cannot succeed by design; its expected behavior is an explicit failure (needs_external), which the report counts.

Latency runner (spec 0.28, #33). `scripts/latency_benchmark.py` measures the local path: one gateway started with `relaymind serve --config`, the routing cache off, no external model, concurrency one. The prompts are `evaluation/latency_prompts.v1.json`: twelve short English prompts, each labeled as a simple tool task (expected to complete), a clarification (expected to wait for input), or a routing prompt (expected to route external, so without an external model it ends as needs_external after the local routing decision). Each request is a compatible chat request with stream true (section 7.3). Before the warm-ups the first request after the gateway starts is recorded as the cold request, apart from the measured runs. Three warm-up requests follow and are not measured; then ten runs per prompt in an order shuffled with a recorded seed. A run that waits for input is cancelled with the native cancel after its sample is taken, so the next run can start. The metrics of section 12.1 are taken this way:

- First transport event and first answer token: from the client's monotonic clock, from just before the request is sent to the arrival of the response status and of the first chunk with nonempty content.
- First model action and first useful content: from the run's trace, as elapsed_ms (the gateway's monotonic clock from run.accepted, section 8): the first validated model-made route, clarification, or tool proposal (as in the demo UI timing, section 9), and the first answer.delta after a successful tool result, or the clarification.required event.

The two clocks are never subtracted from each other. A request that has no response within the per-request time limit is a timeout; a transport error, an error status that the prompt's label does not expect, or a run that ends other than its label is an error. Both are recorded with the sample, never dropped. Each metric reports p50 and p95 by the nearest-rank method (the ceil(q n)-th smallest of the n values present), its sample count, and the timeout fraction (timeouts over all measured requests), overall and per prompt label. The hypothesis is checked on the first model action of the measured runs. Cold startup reports the llama-server start to its first healthy /health response (it includes the model load), the model load time printed by the runtime when it prints one, the gateway start to its first healthy /healthz, and the cold request. The export records the runtime's /props response (context and default sampling), whether the adapter sets cache_prompt (the runtime's prefix cache behavior), and the cached_tokens of every measured model call.

Phase 2 configurations and device classes (spec 0.31). The corpus and latency runners take the phase 2 options as labeled configurations, each a launch-file key (section 14.1), and record them in the export: answer_pass, calls_per_generation, prefetch, answer_stream, early_headers, placement.policy, the selector chain, the enabled fixed parallel workflows, and whether a local model is configured. The baseline of section 12.3 is the configuration before this revision, reproducible by the keys: answer_pass final, calls_per_generation one, prefetch false, answer_stream buffered, early_headers false, placement local_first, chain model_router; the layout and warm-up changes of sections 6 and 10 are code, so a before-and-after comparison names the application revisions. Each configuration is reported apart and never merged with another. The runners accept a timing-sample file, seeded or carried over from an earlier run, and an external model with, optionally, its declared request options (external_model.request_options of section 14.1, given as one JSON object, checked as the launch file checks them, and recorded in the export configuration only when declared, so a configuration without them keeps its identity; spec 0.46), so the placement rules can be exercised in a run that starts a new store per case; the samples used are in the export, and without them placement records predictions and skips nothing. Results are reported per machine, labeled with the class the gateway measured on it (suitable, unsuitable, or none; section 1); a class is the measurement of that machine, never a claim about other machines, and no hardware type is required for a class. A constrained configuration of one machine, such as a CPU-only runtime with fewer threads, is a valid way to measure the unsuitable class: its extra runtime arguments are recorded in the export with the thread and backend settings above, and it is reported as that configuration of that machine, never as another machine. The unsuitable class is any machine or configuration on which the warm-up or the recorded local stage outcomes show that local work does not fit its budgets (RM26, spec 0.48). The expected skill of every corpus case is a sidecar file, `evaluation/corpus.v1.skills.json`, frozen with its own digest in the lock file, so corpus version 1 and its results stay comparable and the case file does not change. A run that used an out-of-process selector is reported in its own column (RM28). The latency runner also records the cold request's first-token time and, with warm-up on, the warm-up samples; the cached-token counts it reports are the ones section 6 reads, and a run of the runner before that change is reported as not measured for them.

Release record (spec 0.28, section 14). `docs/RELEASE.md` is the release record. It lists, in separate sections, the implemented behavior, the passing deterministic tests (with the command and the count), the measured live results (each with its machine, date, and export), and the unmet or unmeasured targets, including platforms that were not run.

### 12.3 Gates and experimental targets

Hard acceptance gates are all deterministic contract and authorization tests passing, successful live local skill-and-tool traces for all three simple demo skills in English (Chinese live results are reported but do not block acceptance), correct handoff without duplicate completed operations, a working model substitution test, and a reproducible benchmark report from both target platforms.

Proposed model-quality targets are at least 80 percent successful local completion on the English simple subset, at least 95 percent correct tool-and-argument proposals on that subset, and no missed mandatory confirmation in the bounded test corpus. Chinese results, when present, are reported per language against the same targets but do not block acceptance. Report exact numerators and denominators. Passing a small corpus does not establish a production reliability guarantee.

The 500 ms target and quality percentages are experimental outcomes, not pre-existing facts. If a target fails, retain the evidence, qualify the candidate as unsuitable for that claim, and compare another model or narrower skill scope. Do not silently substitute a larger model while continuing to label results Qwen3-0.6B.

Phase 2 hypotheses (spec 0.31), stated as experimental targets, not facts: the draft answer pass raises local completion on the English simple subset without lowering task success; prefetch and several calls per generation lower the generations per completed complex run; completion criteria in the external request lower corrections per completed run; early headers give a chat client its run reference before the first answer generation; live streaming lowers first useful content in the none class at task-success parity with buffered; on an unsuitable machine, auto with the class detected has lower p95 first useful content and completion than local-first auto without it, at equal task success (spec 0.48: once the class is unsuitable, auto is managed external execution under every policy, so section 14.4.7 defines how this is measured); the example matcher's English selection Jaccard is at least the local router's, on the corpus and, under the router's eight-skill cap, on the skill benchmark of section 12.4; a selector's narrowing raises the precision of the local model's tool proposals on the tool benchmark without lowering their recall; and, in every configuration, external calls and tokens per completed task are reported next to task success, because the objective is the best use of the external model, not more of it. A missed target is a finding. Every default of this revision is the pre-revision behavior. A hypothesis that holds in its run makes its option a candidate default (spec 0.45): the next revision changes the default only when, in the same run, the option's paired full auto corpus cohort has at least as many task successes as the baseline's (gains at least losses, every planned case in the denominator), and records the numbers either way. Task success in these hypotheses means that full cohort, never a subset chosen after the run. Section 14.4.6 records the decisions of the first measured run.

### 12.4 Selection benchmarks (spec 0.31)

The ops corpus of section 12.2 has six skills and seven tools, which cannot tell a good selection system from a poor one, and no existing benchmark measures this task. RelayMind's selection benchmarks are therefore its own, built from two public datasets, SkillsBench and ToolRet-Training-20w, by the derivations below. They measure, on many more skills and tools, which system is useful: the default (the local model's routing generation, RM02, and its tool proposals in the skill stage) against the example matcher and against a third-party selector, every one run through the RM28 interface on the same frozen files, so the comparison is the same for all. They measure selection in their sources' domains (office and coding tasks, web APIs), not the ops demo, and every report says so; their results are never merged with the corpus of section 12.2.

Skill selection. The source is SkillsBench (benchflow-ai/skillsbench, Apache-2.0), pinned to the git commit and the per-task digests of its registry.json. Derivation: for every active task, the body of task.md is the request; the skills bundled under environment/skills/ are the expected set, because the task's authors chose them and the benchmark's own rule forbids naming them in the prompt; the catalog is the union of all bundled skills, deduplicated by name with the description of its SKILL.md (a skill bundled under several tasks with differing files is kept once, the first in task order, and the difference is recorded); a task with no bundled skill is excluded and counted. The derived file is evaluation/skills.v1.json, checked in with attribution, the pinned commit, and a SHA-256 lock, like the corpus. Example requests for a selector that uses them come from the other tasks that bundle the same skill (leave-one-task-out), never from the case's own prompt. The catalog offered is the whole pool for a selector without a size limit; the local model router offers at most eight skills (section 4.2), so each case is run for it with a catalog of eight, the expected skills plus distractors sampled with a recorded seed, and the report states that the router was measured under its cap. A request over the router's input cap takes the bypass (section 4.1) and is counted as such, never dropped. Metrics. The predicted set of a case is the result's candidate skill and its alternatives (empty for a result of none or clarify). The main metrics compare it with the expected set E: precision |P∩E| / |P|, recall |P∩E| / |E|, and Jaccard |P∩E| / |P∪E|, each 0 for an empty predicted set, macro-averaged over cases, with the micro averages beside them. The model router selects one skill, so its predicted set has one member, and a task that bundles several skills bounds its recall; the report says so. Diagnostics reported with the main metrics: the none-rate, the invalid-output rate of the model router, the bypass count, selection latency per case (monotonic), and the model router's input tokens. Results are reported overall and per SkillsBench category and difficulty, from the task metadata.

Tool selection. The source is ToolRet-Training-20w (the ToolRet training set, Hugging Face mangopy/ToolRet-Training-20w), pinned to a dataset revision. Its licence is not stated on its card, so no row is checked in: the tool lock, evaluation/tools.v2.lock.json, holds the pinned revision, the sampled row ids, the sampling seed, and the SHA-256 of each derived case, and the runner fetches the revision, derives the cases, and refuses a case whose digest differs. The sample is a frozen random sample of 500 rows, stratified by the number of positive tools (one, two to three, four or more). Derivation: the request is the row's query (its instruction field is recorded in the export but not given to a selector, because RelayMind requests carry no such instruction); the candidates are the row's positive and negative tools, normalized to the gateway's tool declaration (name, description, an input schema from the tool's parameters with additionalProperties false; an entry in the RapidAPI style is mapped from its required and optional parameters) and registered in a benchmark-only registry whose handlers never run; normalized names that collide get numeric suffixes in the order of each declaration's digest, with a seeded hash between equal declarations, so a name never shows whether a candidate is positive (evaluation/tools.v1.lock.json, whose suffixes followed source order with the positives first, has the same rows and is kept only to reproduce the runs recorded with it, spec 0.37.1); one synthetic skill per case allows exactly the candidates, so the selection interface and the skill stage see them as they would see any skill's tools. Two tracks. The narrowing track scores the set of tools a selector keeps against the positives with precision, recall, and Jaccard, with completeness (every positive kept) and latency as diagnostics; the default model router does not narrow, so its kept set is every candidate (recall 1, precision the share of positives among the candidates), which is the baseline a narrowing selector must beat. The track needs no model; its scoring code runs in the default test suite on synthetic fixture cases written for the test, and the real sample runs on demand, because no dataset row is checked in. The proposal track scores the set of tools that the first skill-stage generation of a live model proposes (the local model under its budgets, or the external model; several calls under calls_per_generation many) against the positives with precision, recall, and Jaccard, with schema validity (proposals not rejected with unknown_tool or invalid_arguments) and the bypass rate (a candidate set over the model's input limit is counted, never dropped) as diagnostics; the proposal track is run with the full candidate set and again with the set a selector narrowed, which measures whether narrowing helps the small model. Argument correctness is not graded, because the source carries no reference arguments. A first generation that exceeds the configured calls_per_generation limit is invalid_output and contributes an empty predicted set to precision, recall, Jaccard, and completeness. Its returned tool names, proposal count, usage, and schema-validity results remain recorded as evidence; a budget rejection does not itself make a proposal schema-invalid. This rule does not remove proposed names from the set metrics solely because their tool name or arguments fail schema validation. When tool narrowing errors, times out, or returns invalid output, the full-candidate proposal arm may still be measured; the narrowed arm records the narrowing failure with an empty predicted set and no model invocation, and remains in the denominator. A schema-valid none or clarify result is an abstention, not a narrowing failure, and may be measured with its empty tool set.

Retired plan benchmark (spec 0.47). The planned evaluation/plans.v1.json derivation and workflow-plan track are removed with RM30. The existing skill and tool selection benchmarks, their locks, and their historical results remain unchanged. OpenClaw evaluation follows section 12.5 and does not relabel managed-skill corpus results as host-tool results.

Protocol. scripts/selection_benchmark.py runs every selector through the SelectionRequest and SelectionResult shapes (RM28), the built-in ones in process and a third party over the HTTP transport, with the same files; the export records the selector's name and version, the files' digests, the seed, the machine manifest, the timing of every case, and, for a model, its manifest or endpoint; a run that times out or errors is recorded with the case, never dropped. Results of different selectors on the same file version are comparable; results on different versions are never merged, and a changed case is a new file version recorded in the changelog. A selector trained or tuned on a source's data is reported with that fact next to its scores, because its result on that source is not held out; models fine-tuned on ToolRet-Training-20w exist.

Task fixtures (spec 0.50, #139). The tasks are one versioned file, `evaluation/openclaw_tasks.v1.json`, frozen by the SHA-256 digest of its canonical JSON (RM07) in `evaluation/openclaw_tasks.v1.lock.json`; the runner refuses a file whose digest differs, and a changed task is a new version. The file freezes the arms, the repeat count, the sampling seed, the time limit of one attempt, and the host release. Each task has an ID, a kind (text or host_tool), a language (en, or zh linked to its English task and marked best_effort), the prompt the operator gives the host, the sandbox files written to a fresh working directory before each attempt, the host's exec policy (deny or full; a headless ask policy fails closed and is not used), the expected host tool calls (groups of acceptable calls, each argument an exact value, a suffix, a substring, or any value), the expected sandbox files after the attempt, the required and forbidden evidence in the host's final answer, and a rubric in words. Arms and order (spec 0.50). The arms are `direct` (the host's own provider entry for the external model), `relaymind_external_only` and `relaymind_auto` (the plugin with that execution mode, against a gateway launched with the same external model and the local model; relaymind_auto needs both, so without the external model or a usable local model it is not_run, and relaymind_external_only without a local model is launched without it and labeled so), and `relaymind_no_local` (the plugin in auto, against a gateway launched without a local model). Each arm has its own isolated host home and its own gateway; budgets and runtime defaults are the launcher's. The sampling order comes from the seed: in each repeat the tasks in a shuffled order, and for each task its arms in a shuffled order, so the arms of a task run next to each other. An arm that cannot run (no external credential, no local model) is recorded as not_run with its reason and keeps its place; the order of the other arms does not change.

Grading (spec 0.50). An attempt succeeds when the host ended within the time limit with exit status 0, its final answer contains every required evidence group and no forbidden evidence, the host reports each expected tool among its tool calls, the sandbox ends as expected, the host's reported provider and model are the arm's, and, in a RelayMind arm, the gateway started no tool, every run of the attempt is correlated, and each expected tool has a gateway tool proposal of that tool name (the name rule the host's tool report gets in every arm). The host's ok and status fields never decide a success (the pinned host reports ok true for a denied tool), and a host that ended with exit status 130 or died of SIGINT (on Windows, ended by Ctrl-C with STATUS_CONTROL_C_EXIT, 0xC000013A) is recorded as a host interrupt, apart from other exit statuses. An evaluation the operator interrupts still writes its export and report, wherever the interrupt lands (an arm's setup, an attempt, or its grading), marked aborted with the slot it stopped at, or with the arm whose setup it stopped; the attempts that ended are graded, and the interrupted slot and the slots after it, or with an interrupted setup that arm and every slot, are not run, never failures. An attempt the host answered through another provider or model is a host failover: it is counted apart and is never an arm success or a RelayMind answer. A failover needs a provider or model that the host reports and that differs from the arm's; a host report that names neither (the pinned host's error report has both null) is graded as a failed attempt, not a failover. The runs of an attempt are the runs the plugin's diagnostics records name (diagnosticsPath); a gateway run of the attempt's time window that no record names is reported as uncorrelated, and a record without a run ID stays unavailable. A gateway tool proposal is matched to the expected calls by tool name and arguments, and the result is reported, never a failure; a proposal alone is not a completed task. Both arms share one success rule, because a paired comparison compares their successes: the direct arm has no gateway trace, so no arm fails for a call's arguments or for a call outside the expected ones. Those calls are reported per arm and language instead: unexpected host tools (the host's reported tools that no expected call names) in every arm, and unexpected proposals (the gateway proposals that match no expected call by tool name and arguments) in a RelayMind arm, unknown in direct. The host's execution of the call is graded from the host's tool report and the sandbox, because neither the gateway trace nor the plugin's diagnostics records hold the host's tool result or its call ID; no check compares a call ID the gateway issued with the one the host replays (the pinned host rewrites it).

Report fields (spec 0.50). Per arm and language, with exact counts over every attempt (failed, timed-out, and retried ones included): successes, host failovers, timeouts, host interrupts, attempts the host called ok that failed, gateway runs, inference attempts (the diagnostics records; unknown in direct, where the host's assistant turn count is recorded as the host's statement), errors by code, cancellations, needs_external and context_limit_exceeded runs, completed runs without an external call (local turns), the reason codes of the runs that left the local stage (each handoff.started and each needs_external run.failed, such as context_limit or execution_mode), local and external model calls, unexpected host tools, and unexpected proposals (unknown in direct). Zero local turns is a result and is reported with those reasons, never left out; a local-inference comparison whose RelayMind arm had no local turn compares no local inference, and the report says so. Completion latency is the runner's clock around the host command, so it includes host startup and host tool time; first useful content is the gateway's clock, the elapsed_ms of the first answer text or complete tool proposal in the attempt's first run, and unknown in direct; the two clocks are never subtracted from each other. Each has p50 and p95 by nearest rank and its sample count. Tokens are counted per model from the gateway's model.finished usage, summed only over the calls that report a count, with the calls whose count is unknown counted beside the sum, over all attempts and over successful ones; host-reported usage stays apart under the host's label and is never added to a gateway count. The paired comparisons are relaymind_external_only against direct (integration overhead) and relaymind_auto and relaymind_no_local against relaymind_external_only (local inference), on the task and repeat pairs that both arms completed, beside both arms' success counts. Chinese results are reported apart. The export holds every attempt raw (the host's JSON report and output tail, the diagnostics records, the runs with their trace events, the sandbox after the attempt), the fixture digest, the machine, the application revision, the host, Node, plugin, and model identities, and the configuration; it never holds the gateway token or the external credential.

A key named api_key, or any key that is not listed above, is refused. A missing credential is not a startup error, because the adapter reports it as unavailable at call time and readiness shows it (RM16); the launcher does not read or print its value.

Startup is all-or-nothing and runs in this order: read the file, which checks every key, type, and the data mode; check the bind address; when a local model is configured, verify its artifact against its manifest (the file hash, and for a GGUF file the tokenizer and chat-template hashes, section 6); open the sandbox and register the demo tools; load and validate every skill package against them; check policy.enabled_workflows against the registered fixed workflow IDs; open the run store; build the orchestrator. It then runs restart recovery (section 5) exactly once, before the server socket exists, so no run is accepted first, and then, with a local model and placement.warmup true, the warm-up generations of section 6, bounded by warmup_seconds; a runtime that is not ready in time is not a startup error. When recommendations are enabled (section 14.5), restart recovery also covers recommendations and index jobs, and the server opens once a committed lexical catalog is usable, or reports honest empty or unavailable status; the warm-up generations then run as separately reported work instead of before serving. Any failure before that point, including a public bind address, a manifest hash mismatch, an invalid skill package, an unknown fixed workflow ID, a selector endpoint outside loopback, a file with neither model table, local_only or parallel_demo in allowed_modes without a local_model table, a budget of the wrong type or range, an undeclared or unknown data mode, an unreadable file, an unknown key, a sandbox seed that cannot be read, and a run store that cannot be opened, stops the command with exit status 2 and one explicit message on standard error that names the cause, and no socket is opened. The message never contains a credential or a token, and a refused command-line argument is not echoed, because it may be one.

After recovery the launcher creates the application token (section 7.1) by building the app, prints it once to standard output as one line, `Application token: <token>`, together with the bind address as a URL (an IPv6 literal in brackets), and then serves until stopped. It writes the token nowhere else: not to a log, a file, or standard error. When recovery ended unfinished runs, the launcher also prints how many, so the operator can see them in the store.

## 14.2 Placement execution contract (spec 0.39)

These details govern RM27 and the referenced sections, preserving historical trace compatibility.

### 14.2.1 Prediction details (RM27)

For a local generation, an available prediction MUST use the token count of the actual messages and offered tool schemas, measured with that local model's tokenizer before dispatch. An already measured count MAY be reused only for the identical request. It MUST NOT be a byte count, character count, or the count of a representative prompt. Prediction/tokenization time is ordinary active execution time; no generation is charged merely for counting. Failure of a tokenizer request made solely for placement makes the prediction unavailable; it MUST NOT introduce a new capability failure or change local_first/local_only execution. Existing mandatory routing tokenization/capability checks retain their existing failure behavior.

The estimator MUST use retained successful local timing samples for the same model and purpose. Its selected cache class is that of the latest successful sample for that model and purpose: warm when cached_tokens is positive, cold when it is zero, and unknown when it was not measured. Unknown MUST NOT be treated as cold or replaced by an older known class. Prefill and decode throughput come from the selected class's positive measured rates of section 8. Startup warm-up and probe samples MAY supply throughput and cache-class evidence, but MUST NOT supply the expected production output length.

Expected output is the median known output_tokens of successful `kind=run` samples of that model, purpose and actor local, including a truthful measured zero. When none exists, it is the explicit output cap of the actual generation request: routing_output_tokens for routing, or the request's effective max_output_tokens for another purpose. When there is neither a production measurement nor an explicit cap, expected output is unavailable. The gateway MUST NOT invent a skill/repair/final cap or change an adapter request to create a prediction. A measured expected output is limited to an explicit request cap when one applies; otherwise it is used unchanged. The trace identifies run_samples, purpose_cap or unavailable as its source.

With input count I, expected output O, positive measured prefill rate P and decode rate D (tokens/ms), predicted_ms is `ceil(I/P + O/D)`. It is at least one millisecond. A prediction is unavailable when I, O, the selected known cache class, P or D is unavailable, or the calculation is not finite. Unavailable predictions are null, never zero or a default number of milliseconds. Both rates are required even when I or O is zero. Rates are empirical estimates, not promises; the effective-prefill statistic already uses total input tokens, so the predictor MUST NOT subtract cached_tokens from I again.

The estimator MUST preserve the section 8 generic timing statistics of specification 0.38. In particular, `TimingEstimate.median_output_tokens` includes warm-up/probe samples and MUST NOT silently become a production-output statistic. A distinct production-output estimate or filtering validated raw timing samples implements the rule above.

`local_first` records predictions but applies no placement rule or probe. `local_only`, and any run with no configured external path, likewise record predictions but skip nothing and apply no placement deadline, irrespective of the configured policy. Existing stage/run limits still apply. An external endpoint being temporarily unready does not erase a configured external path; existing dispatch/readiness and disclosure checks still govern a subsequent handoff. External_only never performs local placement work. Client-owned execution retains its current ownership/tool contract; a local generation made by it uses the same applicable per-generation placement admission, but no managed skill or success rate is invented for it.

Under device_aware and expected_wait, an unavailable prediction starts the generation under its existing budget and no placement deadline. A stale available estimate remains usable; staleness schedules an idle refresh, never a probe on the user's request. A prediction strictly greater than the remaining local-stage time prevents the generation from starting. This hard cap is checked before expected_wait. An allowed local generation has a placement deadline of `min(predicted_ms * margin, remaining stage milliseconds, remaining run milliseconds)`; comparisons use unrounded monotonic durations, while recorded duration limits round up to integer milliseconds. Budget checks run before placement admission and again before actual dispatch. No rule moves a budget.

Under expected_wait, after the hard cap, a selected skill with both observed local outcomes on this local model and external cost observations for this configured external model runs locally only when `predicted_ms < local_success_rate * expected_external_ms`. expected_external_ms is the median retained successful `kind=run` external-call duration for that external model and actor external, across purposes, multiplied by `max(1, median_external_generations)` from that skill's completed external runs. A known zero local success rate therefore declines local work. Without every required observation, this rule is unavailable and the policy uses device_aware alone. Routing before a skill is selected, client-owned calls and calls without a selected managed skill do not apply this rule. Predictions are unchanged by the rule and the experiment stays labeled placement_policy expected_wait.

### 14.2.2 Trace fields (section 8)

For events written under 0.39, the placement value is a closed object with **all** these keys; nested inputs is also closed. No prompt, endpoint credential or tool-result text is included. Counts reject booleans. Numeric rates/ratios reject NaN/infinity. Older events without the new optional field remain valid.

```text
placement = {
  role: "local" | "external" | "none",
  reason: "local_first" | "local_only" | "no_external_path" |
          "prediction_unavailable" | "within_budget" | "local_slow" |
          "expected_wait" | "external_path" | "no_generation",
  predicted_ms: integer >= 1 | null,
  deadline_ms: integer >= 1 | null,
  inputs: {
    model: nonblank string | null,
    purpose: nonblank string | null,
    input_tokens: integer >= 0 | null,
    input_source: "tokenizer" | "routing_sample" | "none",
    expected_output_tokens: finite number >= 0 | null,
    output_source: "run_samples" | "purpose_cap" | "unavailable",
    cache_class: "warm" | "cold" | "unknown",
    sample_count: integer >= 0,
    sample_recorded_at: UTC timestamp | null,
    prefill_tokens_per_ms: finite number > 0 | null,
    decode_tokens_per_ms: finite number > 0 | null,
    local_success_rate: finite number in [0,1] | null,
    expected_external_ms: finite number >= 0 | null
  }
}
```

The inputs describe the local generation being considered; model/purpose identify that local target even when role none means it was declined. sample_count is the successful sample count in the selected known cache class, and sample_recorded_at is the latest successful same-model/purpose sample that selected the class. An unknown latest cache class uses sample_count 0, null rates, and its recorded timestamp. local_success_rate/expected_external_ms are null unless the expected_wait rule had both observations. `input_source=routing_sample` is allowed only in readiness, never in a run trace's actual placement calculation.

role local means a local generation started or was admitted to start; role none means no routing generation or a declined local generation. local_slow identifies a hard-cap decline; expected_wait identifies a decline by that rule; both have null deadline_ms because nothing started. A started generation has reason local_first/local_only/no_external_path when exempt from rules, prediction_unavailable when the estimator was unavailable, or within_budget when rules admitted it. The exemption reason takes precedence over availability of the estimate; prediction remains truthful/null independently. Deadline is null for all exemptions and unavailable predictions. A native external model.started uses role external, reason external_path and null local prediction/deadline, with every input null except input_source none, output_source unavailable, cache_class unknown and sample_count 0. A route that ran no routing generation and had no declined routing candidate uses role none, reason no_generation and the same empty inputs. An external route selected by a completed local router retains that router's local placement; the object describes the routing call, not the skill's later dispatch.

Every actual local model.started MUST carry its placement; external model.started MUST carry the external marker. model.finished MUST carry predicted_ms and deadline_ms copied from model.started plus boolean deadline_missed. They are null/null/false for a normal external generation. A local timed-out generation retains the original values with deadline_missed true; no model.started or model.finished event or timing sample is fabricated for a generation declined before starting.

route.selected MUST carry the placement of the accepted selector's routing generation, or the most recent declined model-router generation when that explains falling through, or the no_generation marker. A cached route or a deterministic selection made without a preceding model-router decline uses no_generation. If a local skill/final/repair generation is declined after the route already exists, its full placement MUST be carried by handoff.started; if external dispatch is blocked and there is no handoff.started, run.failed MUST carry it. These are additive optional placement fields in the two event schemas, necessary to retain a prediction for a call that never started. A handoff caused by a deadline miss MAY carry that same call's placement; actual duration remains on model.finished.

run.accepted MUST record placement_policy, and these exact dotted numeric keys in budgets: `placement.margin`, `placement.probe_after_seconds`, and the existing `selection.timeout_seconds`. It MUST NOT create a nested placement table inside budgets. margin/probe_after_seconds are finite numbers strictly greater than zero, booleans rejected; defaults remain 2 and 600. The configured policy is recorded even when a particular mode/path is exempt from its rules.

### 14.2.3 Selector propagation (RM28)

A pre-dispatch placement decline of a model-based selector is a gateway-defined `not_placed` outcome, not an invalid selector response. The chain MUST continue in configured order and preserve the attempt. It MUST NOT automatically insert a different selector or make an external routing generation. Successful later admission is handled normally, with the declining routing placement preserved on route.selected. When the chain ends, a rejected model-router output retains existing invalid_output precedence; otherwise a not_placed attempt makes the gateway's exhausted-chain decision route external, skill_id null, reason local_slow (and its route.selected carries mechanism selector_chain); otherwise the existing selection_failed decision applies. A selected skill whose later local generation is declined is handed off with that skill and reason local_slow, including when expected_wait caused the decline.

Only the gateway's explicit pre-dispatch placement-decline signal can become not_placed. BudgetExceededError, unavailable capability, provider failure, external cancellation and other callback stops MUST keep propagating as before. A selector cannot forge or swallow a gateway stop; the chain's existing stop guard continues to enforce it. A deadline miss after an actual routing generation started is an escalation with local_slow, not not_placed, and no cancelled output is admitted.

### 14.2.4 Timeout and error precedence (sections 7.3 and 11)

1. A native/user/chat-disconnect/server-shutdown cancellation remains run.cancelled/cancel_requested; it MUST NOT become a placement escalation even when deadlines coincide. Stop dispatch and request provider cancellation through the existing best-effort path.
2. Already-exhausted generation/time/tool budgets retain their existing checks before admission. If the entire-run time is the limiting deadline, its existing entire-run budget/error mapping wins a tie; do not start an external generation with no remaining run budget.
3. Otherwise an applied placement deadline, including a tie with the local-stage limit, expires as local_slow, deadline_missed true. Ask the adapter to cancel once, retain model.finished plus an unsuccessful timing sample and all completed tool evidence, and discard the generation's partial proposals/text from admission/publication. It escalates before answer commitment under the existing policy/disclosure/context/remaining-budget checks. If that handoff cannot occur, needs_external retains reason local_slow. A local placement miss alone does not mark the local runtime unavailable.
4. A stage/external timeout when no placement deadline applied retains the existing local_budget/external_failed mappings. local_first and local_only remain observational with respect to placement and retain their pre-0.39 timeout behavior.
5. Once an answer.delta has committed answer ownership under RM20/RM32, no placement stop may hand off or replace the answer. Reserve this integration contract for live streaming: a post-commit placement miss ends the run with error_code external_failed, reason_code local_slow, budget `placement.deadline`; the SSE error code is deadline_exceeded with fixed text and reason_code local_slow, no finish chunk and no [DONE]. This follows the existing distinction between a failed run's code and its deadline response code. Its model.finished still says deadline_missed true. No new public error code is introduced. Task #125 must enforce it when live output becomes possible; #130's buffered paths have no committed output before generation completion.

When a cancellation-resistant adapter ignores its timeout, late output MUST NOT be admitted as success: the generation's elapsed applied deadline and task cancellation state are checked after iterator termination. There is no second local/external dispatch while that gateway generation task is still alive. Provider-side cancellation itself remains best effort, as already specified.

### 14.2.5 Readiness (section 7.4)

GET /readyz retains the existing top-level ready, modes, models and local_model. Add this closed top-level field:

```text
placement = {
  policy: "local_first" | "device_aware" | "expected_wait",
  representative: true,
  routing: <the closed placement object above>,
  routing_fits: boolean | null,
  auto_model: nonblank model_id | null
}
```

Readiness has no user prompt. Its routing input is the known input_tokens of the latest successful routing timing sample for the configured local model and actor local, irrespective of kind; it MUST label input_source routing_sample, never tokenizer. Output length/rates use the same production-output and throughput rules above, with routing_output_tokens as the fallback output cap, and a fresh full stage budget as the comparison limit. If that latest routing sample has unknown input count, there is no representative input; it MUST NOT silently substitute an older known count. Unknown input/rates/cache class produce predicted_ms null and routing_fits null. A known prediction uses routing_fits `(predicted_ms <= active_seconds*1000)`. This is a representative planning estimate, not a promise that a future request fits, and MUST be labeled that way in consumers.

No generation or tokenizer request is made for readiness. Existing adapter health requests remain allowed. Under a ready/usable local class, auto_model is the local model under local_first or when there is no configured external path; under the other policies it is external when the representative estimate exists and does not fit, and local when it fits or is unavailable. An absent/unavailable/unsuitable local class keeps the existing RM26 external choice; readiness then predicts no local routing, so routing is the no_generation marker and routing_fits is null. With no such chosen configured model, auto_model is null. The auto mode's readiness is the health of this chosen model, subject to existing operator mode restrictions; overall HTTP 200 still requires every permitted mode ready, otherwise 503. local_only and parallel_demo retain their existing RM26 health requirements, and expected_wait cannot choose on a skill success rate in readiness because no skill is selected. Readiness's routing.role is the predicted auto routing placement (local or none if routing is skipped), with reason local_slow for a representative hard-cap skip; it does not claim an actual generation ran.

### 14.2.6 Idle probe (sections 5, 6, 11 and 14.1)

Only device_aware and expected_wait with a configured local model and configured external path schedule idle probes. An estimate older than probe_after_seconds, or no successful estimate, may trigger one routing-shaped generation when there is no active run. Probe freshness uses the latest successful routing sample; it is not refreshed by repeatedly reading readiness. The probe runs outside any user run, with no user run_id, no trace, and no charged run/stage generations or active time. Record the actual attempt as a ModelTiming kind probe, actor local, with truthful nullable measurements and success independent of any user task.

The probe timeout is `min(placement.warmup_seconds, budgets.active_seconds)` with the existing routing token cap. The reservation and last attempt timestamp are persisted separately from the timing samples. No new sample is fabricated merely because a reservation was taken. A completion, failure or cancellation imposes a cooldown of probe_after_seconds before another attempt, so a cancelled stale probe does not immediately defeat a foreground retry.

A SQLite-wide exclusive probe reservation MUST be acquired in the same transaction that checks no active run and no other probe. All transitions that acquire a foreground run slot, including client-owned acceptance and both resume kinds, MUST atomically refuse while a probe owns that reservation. A valid foreground acquisition attempt blocked by a probe requests its cancellation and returns the existing 429 overloaded, creating no run/key and consuming no approval. The 429 cause is another active run or an idle maintenance probe holding the execution slot; requests are not queued behind maintenance. Existing authentication, body, mode, idempotency, version/state/token/expiry precedence remains unchanged.

The reservation is released only by the matching owner/token after its generation task/iterator has ended, including cancellation cleanup. A bounded cancellation wait does not authorize early release. Provider cancel uses the existing best-effort bounded request. A task that ignores cancellation may keep admission at 429 until it ends or the process genuinely restarts. No TTL automatically expires a live reservation. On shutdown stop scheduling, request cancellation, perform the bounded cleanup and keep the reservation if the task cannot stop. Genuine startup recovery, before the socket and only after the previous server process has ended, removes an orphan reservation; ordinary RunStore open does not. The current single-server lifecycle is retained; this change makes no claim of safely running restart recovery while another server is live on the same store. No inference overlap is promised beyond the existing best-effort provider cancellation contract.

## 14.3 Loopback HTTP selector contract (spec 0.40)

This section extends sections 4.1, 8, 12.2, 12.4 and 14.1 for RM01, RM02, RM08, RM12, RM18, RM22, RM25, RM28 and AC22.

### 14.3.1 Configured identity (section 14.1)

An HTTP selector item in selection.chain is a closed table with exactly four required keys: `transport="http"`, `name`, `version`, and `url`. name and version are nonblank strings; names MUST be unique across the chain and MUST NOT equal a built-in selector name. Existing built-in string entries and defaults remain unchanged. The configured identity is authoritative: a SelectionResult MUST name exactly that name and version. A response cannot establish or change its identity. Existing gateway/built-in mechanism reservations remain enforced.

url MUST be an absolute http URL whose host passes the existing loopback-host rule (localhost or an IP loopback literal, never a resolved arbitrary hostname), with a valid port and without userinfo or fragment. Query strings are not required by the protocol; the protocol refuses them as well, keeping credentials out of this unauthenticated local transport. An https URL is refused as an unsupported scheme: TLS adds no protection on loopback, and the gateway has no certificate setting for this transport. Unknown keys, duplicate/reserved names, malformed URLs, unsupported schemes and non-loopback endpoints are startup errors before a socket. Error messages name the setting/cause and never echo a potentially credential-bearing URL. Startup MUST NOT contact the selector or make a model call. Absence of a local model permits HTTP selectors and retains the existing prohibition on model_router.

Example:

```toml
[selection]
chain = [{ transport = "http", name = "example_keyword", version = "1", url = "http://127.0.0.1:8051/select" }, "example_match"]
timeout_seconds = 2
```

run.accepted.selection remains the effective ordered array of selector names. Routing-cache identity uses each configured selector's name/version as before; changing the endpoint alone does not claim to be a selector implementation revision, so the operator MUST bump version when its behavior changes. An HTTP selector's own choices remain ineligible for the model-router routing cache under section 10.

### 14.3.2 HTTP behavior and cancellation (RM28)

Each reached HTTP selector receives exactly one POST, with the already validated/redacted SelectionRequest as JSON and its deadline_ms set to that attempt's allowed duration. No prompt or permission is added outside the published request shape. The client MUST disable environment proxies and redirects. A redirect is an error even when its target appears loopback; no request is sent to its Location. There are no automatic connection/status retries. Authentication headers, gateway bearer token, provider API keys and ambient cookies MUST NOT be forwarded.

Only status 200 with a parsable, schema-valid SelectionResult can be admitted. A connection/read/protocol failure, any other status, invalid JSON, invalid result, mismatched identity or reserved mechanism is an error and falls through. A response body longer than 1 MiB (1,048,576 bytes after content decoding) is an invalid response and also an error; the gateway stops reading at that limit and never buffers the rest. A valid none result falls through as none. A valid but inadmissible skill/tool/mode choice falls through as inadmissible; the gateway retains all existing membership, identifier, permissions, narrowing and confirmation checks. No HTTP response executes a tool or changes a budget.

selection.timeout_seconds is the total per-attempt monotonic time limit, covering connection, response body, parsing/validation and admission, also bounded by the remaining run time. A shorter exhausted run budget is a gateway budget stop, not a selector timeout. Normal selector timeout records timeout and falls through. Cancelling the run aborts/closes the HTTP operation and propagates cancellation; it MUST NOT become error/timeout or start the next selector. Cancellation of this POST does not prove the out-of-process selector stopped its own model work. The gateway has no selector-model cancellation API. HTTP resources close on every path and at app/benchmark shutdown; client ownership must not leak between event loops.

Fixed outcome/error labels may be recorded; raw response bodies, exception messages with URLs, and selector error text MUST NOT be persisted or returned as gateway error messages. Redaction is applied before sending the request and before storing any allowed claim fields. A null/unknown claim is preserved as such rather than fabricated from a transport failure.

### 14.3.3 Exact per-attempt provenance (section 8)

Keep the existing closed route.selected.selector object: name, version, mechanism, elapsed_ms and attempts. The top-level identity/mechanism remain those of the admitted selector, or nulls for an exhausted/aborted chain; elapsed_ms remains the admitted attempt's time or the whole chain's otherwise. Add `cancelled` to the attempt outcome enum solely for a run-cancelled in-flight attempt. For newly recorded attempts the exact closed object is:

```text
{
  name: nonblank configured selector name,
  version: nonblank configured selector version,
  transport: "in_process" | "http",
  outcome: "selected" | "none" | "timeout" | "error" |
           "inadmissible" | "not_placed" | "cancelled",
  elapsed_ms: integer >= 0,
  model_calls_claim: null | [
    { model: nonblank string, call_id?: nonblank string }
  ]
}
```

Each array entry is closed and matches the existing SelectionResult.model_calls item schema; omission of call_id retains its published meaning. model_calls_claim is always null for an in_process attempt: gateway-owned calls are observed separately in model.started/model.finished. For an HTTP attempt it is the schema-valid response's model_calls array **as an unverified selector claim**, even when the response later fails identity/mechanism/admission checks or returns none. A timeout, non-200 response, unparsable body or schema-invalid result has null claims. A schema-valid reported empty array is `[]`, meaning “selector claims zero”, never “gateway verified zero”. A null claim means unknown, not zero. No endpoint URL, prompt, request payload or raw error body belongs to an attempt.

Schema-valid claims are attributed to the configured endpoint/name/version regardless of an inconsistent identity inside the response; the latter still makes the attempt error and grants nothing. Unknown fields inside a model-call claim make the SelectionResult invalid as before. All previous spec-version attempt objects with just name/outcome remain readable; their missing transport/version/claims mean not recorded, never inferred HTTP-free or empty. Update both the Python TraceEvent validator and published JSON Schema together.

Every completed attempt, including one which returns none or is refused, MUST survive in the next route.selected selector summary. There is one existing exceptional path to cover: an earlier HTTP attempt can finish and a later model-router gateway stop can exit the chain before route.selected. In that case preserve the same optional `selector` summary on handoff.started, or on run.failed/run.cancelled when no handoff/route event is written. Include the interrupted current attempt as cancelled only for actual cancellation; a gateway generation/budget failure otherwise uses error and keeps its original gateway failure mapping. This fallback adds no new event type and MUST NOT fabricate a routing decision solely to hold provenance. If a normal route.selected already preserved the complete summary, later events need not repeat it. Gateway cancellation/budget stops continue propagating; recording their attempt does not turn them into selector fallthrough.

HTTP claims MUST NOT enter run.completed.model_calls, external_calls, generation/token budgets, model timing samples, first-model-action latency, placement estimates or model/skill outcome counters. route.selected of a selected HTTP selector has actor gateway and a custom unreserved mechanism, never actor local/external. The gateway can prove only its own observed calls. A run with an HTTP attempt, including error/timeout/none followed by a successful built-in selector, cannot claim fully observed zero external inference calls from an empty self-report.

### 14.3.4 Evaluation and transport reuse (sections 12.2 and 12.4)

### 14.4.7 Unsuitable detection from local stages (specification 0.48; #170)

The phase 2 run of section 14.4.6 measured the constrained configuration
`ready` in every case, although it completed no simple case locally in auto.
Two causes were found in the recorded run stores. The startup check timed only
the routing-shaped warm-up, while a local stage spends the same active_seconds
on a routing generation and at least one skill generation. And the runner kept
one runtime across cases, so after the first case every warm-up found its
prompt in the runtime's prefix cache. This revision adds, under
placement.detect_stages, the skill-shaped warm-up to the startup check and a
rule that reads what local stages actually did (RM26). The key is false by
default, because the measurement below did not support the unsuitable path on
this machine; the stage outcomes are recorded either way.

A local stage outcome is recorded once per run, when the run's local stage
ends, for a run that made at least one local generation of its own (routing
included; a parallel workflow branch is not one, spec 0.38.1) in local_only, or
in auto with the local model ready. The stage ends with handoff.started, or with
run.completed or run.failed while the run is still local. The outcome is "ran out
of local time" when that event has reason_code local_slow (RM27) or names the
budget active_seconds or run_active_seconds, and "fit" otherwise, including a
stop on a generation or tool limit, which measures the model and not the device.
A cancelled or interrupted run, a run.failed with error code internal_error, and
an event with reason code capability_missing (RM04: a local model that failed,
whether the run then ends as needs_external or hands off in degraded mode,
section 11), record no outcome. A stage that waits for clarification or
confirmation records its outcome when it ends. The outcome carries the local
model ID, the run ID, and the time of the ending event; it is derived from the
trace event that the store writes in the same transaction, so the trace proves it.

With placement.detect_stages true, the rule of RM26 reads the latest three outcomes of the configured local model,
in recorded order. When all three ran out of local time and the latest ended
less than placement.probe_after_seconds ago, the class is unsuitable with a
cause that names the count, the budget, and the time of the latest stage.
Otherwise the class is the one startup detection and readiness set. The rule
never changes a budget, never applies to the absent or unavailable classes, and
applies only with placement.detect true. Because a stage that fits ends the
streak and a stale streak expires, one local stage per probe_after_seconds is
the price of noticing that the machine became fast enough again. The idle probe
of section 14.2.6 is unchanged; a model it restores that keeps running out of
local time is classified again by this rule.

Measurement. Under every placement policy, auto with an unsuitable class is
managed external execution, the same path as auto without a local model
(RM26), apart from the class fields of run.accepted and route.selected. A
deterministic test MUST prove that equivalence on the same request. The
hypothesis of section 12.3 is then measured on recorded evidence of one machine
and one revision: the local-first auto cases of a configuration that the rule
classifies unsuitable (control) against the auto cases of the none-class cell
with the same selector chain without model_router (candidate), paired by case
and by latency schedule. The report names both cells, their revision, and that
the arms ran at different times, so provider latency may have drifted, and it
states that startup warm-up time is in neither arm. A live check on the
measuring machine confirms that the startup line and run.accepted report the
class on the configuration. The offline replay of both rules over the recorded
stores is reported per cell, with the longest run of consecutive outcomes that
ran out of local time in each configuration, so the margin of the threshold is
visible. Recorded handoff.started events before this revision carry no budget,
so the replay treats a local_budget handoff whose local_active_ms reached
active_seconds as one that ran out of local time, and says so.

Evaluation runners that start a new run store per case, as the section 14.4
matrices do, see only the startup check: their stores hold no earlier stages.
placement.detect_stages is a launcher key, not a placement policy setting, so it
is not a runner option and the recorded configurations keep their identity.

Result (27 October 2026, `docs/evidence/2026-10-27-unsuitable/`, derived from the
phase 2 package without rerunning a cell; `scripts/analyze_unsuitable.py`).
Replay: the stage rule fires in all 7 constrained corpus attempts, from the
tenth accepted run of the cell in six of them and the thirty-seventh in the
seventh, and in none of the 8 normal ones; the longest run of
consecutive local stages that ran out of local time is 7 to 26 in the
constrained cells and at most 2 in the normal cells, so the margin of the
threshold of three is one stage. The startup check of this revision classifies
the one cold case of each constrained cell unsuitable (3315 + 2281 ms against
4000 ms) and every other case ready, because the runner kept one runtime and the
later warm-ups were served from its prefix cache; the check of spec 0.47
classified every case ready. Hypothesis: not met. Against local-first auto on
the constrained configuration, managed external execution had 43/52 against
45/52 auto corpus successes (3 gains, 5 losses), p95 first useful content
54260 against 53087 ms and p95 completion 55569 against 53424 ms (p50 15827
against 10358 ms and 17605 against 11794 ms), with 6 timeouts and 16 errors
against 0 and 9. The cause is in the traces: a constrained local stage that runs
out of local time has usually run the skill's tool already, and the handoff
carries the result, so the external stage needed 0.83 calls per simple latency
request against 2.27 without a local stage, at 7.4 and 8.1 s per call. On this
machine and external model, running out of local time did not mean that local
work did not help. So placement.detect_stages stays false, every default stays
as in 0.47, and the section 12.3 hypothesis is recorded as not met with these
numbers. A later revision may revisit it with a faster external model, repeated
passes, or a rule that counts the work a local stage leaves for the external one.
A live check on the same machine (`live-check-apple-m1.json` in the same
directory) confirmed both rules with placement.detect_stages true: a cold
constrained runtime was classified unsuitable at startup (3356 + 2271 ms), a
warm one started ready and became unsuitable after three local_only stages that
each ran out of local time, after which auto ran as managed external execution;
the normal configuration stayed ready.

Publish validated metadata and its lexical projection atomically before asynchronous vectors. The canonical eligible projection for each published catalog_revision and selection_scope is validated and serialized once at publication; dispatch reuses those bytes and validates only the per-request envelope fields. Vector keys include exact content/representation/model/config identities. Query pins a coherent catalog and compatible vector entries; additions without vectors are lexical immediately; old/deleted versions are filtered against authoritative current catalog. Failed generation never replaces the last usable one. Corruption with no usable snapshot is unavailable, not ready. Recovery rebuilds derived state from catalog without re-downloading all source originals or clearing feedback.

For recommendations enabled, startup still validates all static settings/artifacts and performs run/recommendation/job restart recovery before accepting work. It opens the service when a compatible committed lexical catalog is usable (or exposes honest empty/unavailable status), then runs generative warm-up as independently reported work. Section 14.1's startup order states this step; disabled configuration keeps the existing order. No inference request bypasses its own readiness/placement policy. A healthy socket or warm-up progress is not useful lexical acceptance (section 12.6). Missing/disabled service returns recommendation_unavailable on create, with unavailable readiness; invalid bodies are still rejected under section 7.6 precedence.

Background dispatch pauses during generative warm-up or active execution-slot work. An in-flight CPU batch must drain under its measured bound; no unsupported preemption promise is made. Busy query embedding reports not_ready for lexical fallback. Record overlap/batch drain, scheduler settings and RM27 actual contended samples; never discard slow samples or relabel them idle. Indexing cannot consume the execution slot or create its spurious 429. The operational gates include all serialization/admission/persistence.

Local rescan detects changes within its configured scan interval, separate from receipt-to-lexical visibility. External jobs run only for a qualified permitted configured source. Failure schedules initial backoff, doubles after each consecutive failed job up to max, resets on success; no same-job retry loop. Refresh staging is bounded under the table, with import visibility workload batches of 25 metadata records. Publish a valid complete source generation atomically. Invalid/incomplete/cancelled/oversized/timed-out stages keep last good revision and record failure counts, last success time and stale status. For initial bounded explicit imports, coverage remains partial until all declared batches complete; that partial import never authorizes omission-based deletions. Larger source inventories must fit explicitly qualified bounds; do not auto-split an over-limit full refresh and infer completeness.

Only explicit complete inventory or documented source tombstones prove removals. A missing page/item in a failed partial fetch does not. Restart marks interrupted jobs and derives replacement work under the same budgets/backoff; shutdown cancels staging, never commits a partial generation. Successful fetch says nothing about current host permissions/availability. Source secrets resolve only inside acquisition transport and never enter metadata, vectors, logs, model context or exports. Acquisition permissions and archive safety are separate from byte integrity. MATRIX-REFRESH remains a named blocker; these finite builder limits do not qualify its interface or legal cadence.
